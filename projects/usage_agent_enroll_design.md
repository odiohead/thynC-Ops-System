# 사용량 수집 Agent — 빠른 설치 · 병원 등록 · 에이전트 관리

> **상태: dev2·DEV 구현 (2026-11-20) — PROD 미반영**
> 관련: [usage_collection_design.md](usage_collection_design.md) (수집 구조 · Agent · 수신부), [usage_overview_design.md](usage_overview_design.md) (전체 병원 화면)

---

## 1. 무엇을 바꾸나

병원 서버에 수집 Agent를 설치하는 일을 빠르게 한다. 이전에는 설치 묶음을 직접 옮기고, 토큰을 따로 발급해 전달하고, DB 계정을 손으로 만들고, 설정 파일을 채운 뒤 점검과 타이머 켜기를 각각 했다.

이후에는 두 단계다.

1. 운영관리시스템 **[사용량 > 에이전트 관리]** 에서 병원을 등록하고 서버 대수를 적는다.
2. 병원 서버에서 한 줄을 실행하고 병원코드와 서버 이름(기본값 = 호스트명)만 넣는다.

```
wget -qO install.sh https://ops.seersthync.com/api/usage-ingest/agent/install.sh && sudo bash install.sh
```

## 2. 결정 사항 (2026-11-19~20 대화)

| # | 결정 | 비고 |
|---|---|---|
| E1 | 설치 파일은 운영관리시스템에서 wget으로 받는다. **주소만 알면 받을 수 있다** | 수신 주소와 같은 도메인이라 병원 방화벽을 새로 열 일이 없다. 설치 파일에 비밀값은 없다(실행 파일에 제품 DB의 표·컬럼 이름은 들어 있다 — 사용자 감수) |
| E2 | 설치 때 묻는 것은 **병원코드 + 서버 이름**. 서버 이름의 기본값은 호스트명 | 한 병원에 서버가 여러 대면 서버마다 같은 병원코드, 다른 이름 |
| E3 | **수집 병원 등록**이 먼저다. 병원 목록에 있는 병원을 골라 서버 대수를 적는다 | 병원명·병원코드는 입력하지 않는다(본체 병원 목록과 같은 값) |
| E4 | **사람이 다루는 토큰은 없앤다.** 등록이 문지기 역할을 하고, 서버 키는 등록 때 자동 발급 | 인증 자체를 없애지는 않는다(§4). 사용자: "토큰구조는 너의 제안대로" |
| E5 | 등록한 자리는 **기한 없이** 열어 둔다 | 자리 수(서버 대수)가 상한 |
| E6 | 설치 중 **"○○병원(HOSP-…)에 등록합니다. 맞습니까?"** 확인을 넣는다 | 병원코드 오타로 다른 병원에 붙는 것을 막는다 |
| E7 | 조회 전용 DB 계정은 설치 스크립트가 만든다 | 기존 서비스에 영향이 없음을 확인한 뒤 반영(§5) |
| E8 | 에이전트 관리는 전체 병원 화면 우측 상단 버튼으로 들어간다. **운영 중인 병원 N곳 중 수집 중 M곳**을 보여 주고, 서버 일부만 수집 중인 병원을 표시한다 | 전체 병원 화면의 병원명 옆에도 '서버 1/2' 표시 |
| E9 | 이미 설치된 서버(병원 토큰)는 그대로 둔다 | 동수원 1대 · 화순성심 2대 |

제안값으로 정한 것(사용자 확인 전):

| # | 제안값 | 이유 |
|---|---|---|
| F1 | '운영 중인 병원' = 병원 상태(`hospitals.status`)가 '운영'인 병원 | 병원 목록의 상태 값 그대로(현재 226곳) |
| F2 | '수집 중인 서버' = 차단되지 않았고 최근 24시간 안에 수신에 성공한 서버 | 전체 병원 화면의 '수신 지연' 기준과 같다 |
| F3 | 변경(병원 등록 · 대수 수정 · 차단 · 재등록 허용)은 ADMIN 이상 | 열람은 사용량과 같은 게이트 |
| F4 | 본체는 원본 DB에 직접 쓰지 않고 수신부의 관리 호출을 부른다 | "원본 DB에 쓰는 것은 수신부뿐" 규칙을 그대로 둔다(§6) |

## 3. 설치 흐름

```
[운영관리시스템]  에이전트 관리 → 병원 등록 (병원 선택, 서버 2대)          → 자리 2개가 열림
[병원 서버]       wget … install.sh && sudo bash install.sh
                    1) 설치 묶음 내려받기 · SHA-256 확인
                    2) 실행 파일 · 서비스 · 타이머 배치, 전용 계정 thync-usage
                    3) 병원코드 입력 → "동수원병원(HOSP-000038)에 등록합니다. 맞습니까? [Y/n]"
                    4) 서버 이름 입력 [기본값 호스트명]
                    5) 제품 DB에 조회 전용 계정 생성
                    6) 서버 등록 → 이 서버 전용 키를 받아 설정 파일에 저장
                    7) 점검(check) → 타이머 켜기 → 첫 실행
[운영관리시스템]  에이전트 관리에 서버가 나타나고, 첫 수신 뒤 '수집 중'
```

- **DB 계정(5)을 등록(6)보다 먼저** 한다. DB 준비가 안 되면 서버 자리를 쓰지 않고 멈춘다.
- **다시 실행하면** 실행 파일과 서비스 정의만 새것으로 바꾼다. 설정에 키가 있으면 등록을 다시 하지 않는다(업그레이드 겸용).
- 점검에서 문제가 나오면 멈춘다. 등록과 설정은 저장되어 있으므로 고친 뒤 다시 실행하면 이어진다.
- 질문은 터미널(`/dev/tty`)에서 받는다. `wget -qO- … | sudo bash` 처럼 파이프로 실행해도 된다.
- **어느 서버로 보내는지는 설치 파일을 받은 주소로 정해진다.** `dev.ops.seersthync.com`에서 받으면 DEV로, `ops.seersthync.com`에서 받으면 PROD로 보낸다(스크립트에 그 주소가 적혀 나온다). 등록과 키는 환경별로 따로다. 다른 환경으로 옮기려면 그 서버의 `agent.env`를 지우고 새 주소의 설치 명령을 다시 실행한다 — 옮기기 옵션은 아직 없다.
- 옵션: `--hospital` · `--server` · `--yes`(묻지 않고 실행), `--db-name`, `--no-db-user`(DB 계정을 직접 준다), `--no-service` · `DESTDIR`(검증용).

## 4. 등록과 인증

수신 주소는 인터넷에 열려 있고 병원코드는 순번이라 추측할 수 있다. 인증이 없으면 누구든 아무 병원 이름으로 기록을 넣을 수 있고, 원본 행은 지우지 않는 규칙이라 되돌리기 어렵다. 그래서 사람이 다루는 토큰만 없애고 인증은 남긴다.

| 단계 | 규칙 |
|---|---|
| 병원코드 확인 | 등록된 병원만 병원명과 남은 자리를 돌려준다. 등록되지 않은 코드는 "등록되지 않은 병원코드" |
| 서버 등록 | 등록된 병원이고 **자리가 남아 있을 때만** 그 서버 전용 키를 발급한다. 자리 = 서버 대수 − 차단되지 않은 서버 수 |
| 같은 이름 | 이미 있는 서버 이름으로는 등록할 수 없다. 재설치는 관리자가 **재등록 허용**을 누른 뒤 같은 이름으로 한 번만 |
| 접속 | 서버 키는 **등록한 서버 이름으로만** 쓸 수 있다. 다른 이름으로 접속하면 거부. 다른 서버가 시작한 실행을 이어 갈 수도 없다 |
| 차단 | 차단한 서버는 키로도 병원 토큰으로도 거부한다. 자리 계산에서 빠지므로 자리가 다시 열린다 |
| 빈도 제한 | 확인 · 등록 요청은 IP당 10분에 30회 (병원코드를 훑지 못하게) |

- 키 원문(`tuk_…`)은 발급 응답과 그 서버의 설정 파일에만 있다. 원본 DB에는 SHA-256만 저장한다.
- 누가 자리를 먼저 가로채면 정상 설치가 "자리가 없습니다"로 실패해 바로 드러나고, 관리자가 그 서버를 차단하면 자리가 다시 열린다.
- 병원 토큰(`tua_…`, `agent_tokens`)은 그대로 동작한다. 병원 토큰으로 접속하는 서버는 에이전트 관리에 '병원 토큰'으로 표시된다.

**남는 약점**: 병원을 등록하고 설치하기 전까지는 병원코드를 아는 누구나 자리를 차지할 수 있다(E5 — 기한 없음). 막는 장치는 자리 수 상한과 에이전트 관리의 서버 목록(이름 · 등록 IP · 차단)뿐이다.

## 5. 조회 전용 DB 계정 — 기존 서비스 영향 확인

설치 스크립트는 제품 DB에 계정 하나(`thync_usage_ro`, 접속 위치 `localhost` · `127.0.0.1`)를 만들고 정해진 표의 SELECT만 준다. SQL은 이전부터 손으로 실행하던 `create-db-user.sql` 그대로이고(이미 설치된 3대에서 실행된 것), 자동화로 바뀐 것은 비밀번호를 스크립트가 만든다는 점뿐이다.

dev2의 MySQL 8.0.46(병원 서버는 8.0.45)에서 실행 전후를 통째로 비교했다(2026-11-20).

| 확인 | 결과 |
|---|---|
| 계정 목록 | 새 계정 2행만 추가. 기존 계정의 행(비밀번호 해시 · 권한 · 잠금 상태)은 그대로 |
| 권한 | 새 계정의 표 단위 권한 56행, 전부 SELECT. DB 단위 · 전역 권한 없음 |
| 제품 표 | 표 목록 · 행 수 · 생성 시각 변화 없음 (아직 없는 연도의 상태 이력 표도 만들어지지 않음) |
| 서버 설정 | 전역 변수 변화 없음 |
| 새 계정으로 쓰기 | 조회는 되고 삭제 · 표 생성 · 시스템 표 조회는 거부 |

- 재시작이나 설정 변경이 없고, 제품이 쓰는 계정과 표를 건드리지 않는다.
- 다시 실행하면 이 계정의 비밀번호만 새 값으로 맞춘다(`ALTER USER`).
- root로 MySQL에 바로 접속되지 않는 서버에서는 관리자 계정을 묻는다(계정을 만들 때만 쓰고 저장하지 않는다). 그것도 안 되면 계정을 직접 만든 뒤 `--no-db-user`로 실행한다 — 이 경우에도 기존 서비스에는 영향이 없다.
- **확인하지 못한 것**: 병원 서버가 MySQL 복제 구성인 경우. 계정 생성 문장이 복제본에도 전달되지만(계정이 하나 더 생김) 그 구성에서 직접 실행해 보지는 않았다.

## 6. 구조

```
병원 서버 ── wget ──▶ Nginx /api/usage-ingest/ ──▶ 수신부 (usage-ingest)
                                                   · GET  /agent/install.sh · /agent/latest · /agent/<설치 묶음>
                                                   · POST /v1/enroll/check · /v1/enroll        (인증 없음, 등록이 문지기)
                                                   · POST /v1/handshake · /push · /finish      (병원 토큰 또는 서버 키)
본체 앱 ── 127.0.0.1 직접 ───────────────────────▶ · POST /internal/v1/enrollments · /enrollments/remove · /servers/action
        └─ 원본 DB 조회 (읽기 전용) ─ 등록 · 서버 · 실행 기록
```

- **원본 DB**(`usage-ingest/migrations/0002_enrollment.sql`): `agent_enrollments`(병원코드 · 병원명 사본 · 서버 대수 · 메모), `agent_servers`에 키 해시 · 등록 시각 · 등록 IP · 재등록 허용 · 차단 컬럼, `agent_admin_secret`(관리 호출 확인 값 1행). 이미 수집 중인 병원은 현재 서버 수로 등록해 둔다.
- **관리 호출**은 수신부가 처리한다 — 본체는 원본 DB에 쓰지 않는다. `/internal/v1/*`은 Nginx가 넘기지 않는 경로이고, 수신부는 (1) 프록시를 거친 요청이 아니고 (2) 같은 서버에서 왔고 (3) 원본 DB에 있는 값을 냈을 때만 받는다. 새 환경 변수는 없다.
- **설치 묶음**은 git에 넣지 않는다(`agents/thync-usage-agent/dist/`). 배포 때 서버의 같은 위치에 복사하면 수신부가 가장 높은 버전을 내려준다. 설치 스크립트에는 묶음의 SHA-256과 수신 주소(요청이 들어온 호스트)가 적혀 나간다.
- **Agent 0.2.0**: `enroll-check` · `enroll` 명령 추가(설치 스크립트가 호출). 수집 동작은 그대로다. DB 계정 생성은 Agent가 아니라 설치 스크립트가 `mysql` 명령으로 한다 — Agent의 조회문은 여전히 조회뿐이다.
- 병원명 사본은 설치 중 확인 문구에만 쓴다. 에이전트 관리 화면을 열 때 본체 병원명과 다르면 맞춘다.

## 7. 에이전트 관리 화면 (`/usage/agents`)

```
에이전트 관리                                                   [← 사용량] [+ 병원 등록]
운영 중인 병원 226곳 중 수집 중 2곳 (1%)   │   등록 4곳 · 일부 수집 1곳 · 수신 끊김 0곳 · 설치 대기 1곳
병원 서버에서 실행하는 설치 명령                                           설치 묶음 0.2.0
  wget -qO install.sh https://…/api/usage-ingest/agent/install.sh && sudo bash install.sh   [복사]

[전체 4] [일부 수집 1] [수신 끊김 0] [설치 대기 1] [수집 중 2]
 병원                         서버 (수집 / 대수)     서버별 상태                                  관리
 화순성심병원 [일부 수집]      1 / 2                  ● seongsim-11 수신 11-20 14:06 v0.1.0       대수 수정
 HOSP-000168                 설치 2대               ● seongsim-12 수신 11-18 13:09 [수신 끊김]   재등록 허용 · 차단
```

| 병원 상태 | 뜻 |
|---|---|
| 수집 중 | 수집 중인 서버 수 ≥ 등록한 서버 대수 |
| 일부 수집 | 수집 중인 서버가 있지만 서버 대수보다 적다 (설치가 덜 됐거나 일부 서버의 수신이 끊김) |
| 수신 끊김 | 받은 적이 있는데 지금 수집 중인 서버가 없다 |
| 설치 대기 | 서버가 아직 없거나, 등록만 하고 한 번도 받지 못했다 |

- 손봐야 할 병원이 위로 온다(일부 수집 → 수신 끊김 → 설치 대기 → 수집 중).
- 병원 등록: 병원 목록에서 병원명 · 병원코드로 찾아 고르고 서버 대수를 적는다. 검색어가 없으면 운영 중인 병원을 보여 준다. 이미 등록한 병원은 나오지 않는다.
- 서버별 조치: 차단 / 차단 해제, 재등록 허용 / 취소. 병원별: 대수 수정, 등록 해제(서버가 없는 병원만 — 받은 기록은 지우지 않는다).
- 전체 병원 화면(`/usage`): 우측 상단 **에이전트 관리** 버튼, 일부 서버만 수집 중인 병원은 병원명 옆에 `서버 1/2`.

## 10. 서버에 올릴 때

1. `git pull` → `npm run build:usage-ingest` → `node usage-ingest/dist/migrate.mjs`(원본 DB에 0002 적용 — 표 2개 추가, `agent_servers` 컬럼 추가)
2. 설치 묶음 복사: dev2의 `agents/thync-usage-agent/dist/thync-usage-agent-0.2.0.tar.gz` → 서버의 같은 위치
3. `pm2 restart thync-usage-ingest-<env>` — 재시작 중 실패한 전송은 Agent가 다음 실행 때 다시 보낸다
4. 본체 빌드 → `pm2 restart thync-<env>`
5. 확인: `https://<도메인>/api/usage-ingest/agent/latest`, 에이전트 관리 화면의 '설치 묶음 0.2.0'
6. Nginx · 환경 변수 변경 없음. 본체 DB 변경 없음
