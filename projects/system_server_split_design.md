# 시스템 품목 수량 관리 전환 + 서버 품목 병상별 분리

> **상태: 설계 확정 — dev2 구현·검증 완료, PROD 미반영** (2026-11-17 작성·승인·dev2 적용)
> 관련: `stock_out_v2_design.md` §13(시스템 구성품, 2026-11-12) — 이 문서는 그 구조 위에서 품목 정의와 재고 데이터를 바로잡는다.

## 1. 배경

- 대웅제약재고의 **thynC시스템10·20·30·40·50·100**은 서버·데스크탑·모니터·사이니지를 묶은 **논리 품목**이다. 실물은 구성품이다.
- 그런데 2026-11-11 재고실사 때 시스템 품목을 시리얼 관리로 바꾸고 **서버 본체의 시리얼(Dell·Lenovo 서비스 태그) 117개를 시스템 품목의 개체로 등록**했다. 논리 품목에 실물 시리얼이 붙고, 실물인 서버 품목(대웅제약재고)은 재고가 0이다.
- 서버 품목은 서버(워크스테이션)·서버(50병상)·서버(100병상) 3종인데, 시스템10~40이 모두 서버(워크스테이션) 하나를 가리켜 **어느 시스템 몫인지 구분되지 않는다**.

## 3. 바뀌는 것

| 서버(20병상)·(30병상)·(40병상) | 없음 | **신규 3종** (ITEM-0082~0084, 분류 '서버', 시리얼 관리, 나머지 속성은 ITEM-0076 복제) |

### 3.2 개체 이관 (117대, 전부 재고 상태·창고 B327호)

| 원래 품목 | 옮길 품목 | 개체 |

| thynC시스템20 | 서버(20병상) | 12 |

| thynC시스템40 | 서버(40병상) | 23 |

| thynC시스템100 | 서버(100병상) | 35 |

- `inventory_units.item_id`만 바꾼다 — 시리얼·창고·등록일 그대로. 서버 품목(대웅·운영팀)에 같은 시리얼이 없음을 확인함(충돌 0).
- **전표**: 시스템 품목의 '재고실사 후 입고' 전표 9건은 **시스템 품목의 수량 전표로 남긴다**(시리얼 연결만 뗌 — 시스템 수량의 근거). 서버 품목에는 **같은 일자·창고·수량·비고의 입고 전표 9건을 새로** 만들고 시리얼 연결을 그쪽으로 옮긴다. 비고에 `[시스템 품목에서 개체 이관 — 원 전표 STK-…]`.
- **재고 수량**: 서버 품목에 창고 B327호 재고 행을 만든다(18·12·13·23·16·35). 시스템 품목 재고 행은 그대로.

### 3.3 구성 설정·구성품 종류

- 구성품 종류: 7종 → **10종** (서버 6 + 데스크탑·27인치 모니터·50인치 사이니지·데스크탑(그래픽카드포함)). 표시 순서는 서버를 병상순(10→20→30→40→50→100)으로 앞에 둔다.
- 신규 서버 3종 + 서버(10병상)의 편입 대상(`source`) = 운영팀재고 서버(워크스테이션) (D1).
- 시스템 × 구성품 설정: 시스템10→서버(10병상) 1, 시스템20→서버(20병상) 1, 시스템30→서버(30병상) 1, 시스템40→서버(40병상) 1, 그 외 서버 칸은 0. 서버가 아닌 구성품 수량은 그대로.

### 3.4 대기 중인 출고요청 (미처리 6건)

구성품에 서버(워크스테이션)이 잡혀 있는 2건만 바꾼다. 나머지 4건(시스템50·100)은 그대로.

|---|---|---|
| SOR-202611-0006 | thynC시스템20 ×1 | 서버(워크스테이션) → 서버(20병상) |
| SOR-202611-0011 | thynC시스템30 ×1 | 서버(워크스테이션) → 서버(30병상) |

## 4. 코드 변경

조사 결과 출고요청·출고 처리 엔진은 품목의 관리 방식(시리얼/수량)을 보고 동작하므로 **데이터만 바꾸면 대부분 그대로 맞는다**.

- 시스템 라인: 시리얼 해제 시 자동으로 수량 모드(재고 많은 위치부터 차감).
- 서버 구성품: 출고분은 시리얼 입력, 미출고분은 시리얼 입력 후 운영팀재고 서버(워크스테이션)으로 편입 — 현행 로직 그대로.

**필요한 변경 1건**: `stock_out_component_kinds.source_item_id`에 **UNIQUE 제약**이 있어 운영팀 품목 1개에 대웅 구성품 1개만 짝지을 수 있다. D1을 위해 제약을 풀고 일반 인덱스로 바꾼다.

- 마이그 `…_stock_out_kind_source_non_unique`: `DROP INDEX stock_out_component_kinds_source_item_id_key` + `CREATE INDEX`.
- `prisma/schema.prisma`: `sourceItemId`의 `@unique` 제거, `InventoryItem.stockOutKindSourceOf`를 목록 관계로. 이 역방향 관계를 읽는 코드는 없음(확인).
- 같은 요청에 시스템10·20이 함께 있어 두 구성품의 미출고분이 같은 운영팀 품목으로 들어가는 경우는 편입 전표가 구성품별로 따로 계획되므로 현행 로직으로 처리된다 — 스모크로 확인(§6).

**화면**: 변경 없음. 출고 처리 카드에서 수량 품목 라인은 '수량 차감 n개 · 현재고 n개'만 나오고, 시리얼 기록 메모 칸은 구성품 출고분 라인에만 있다 — 시스템 라인에는 원래 없다. (작성 당시 "시스템 라인에 메모 칸이 나오니 숨긴다"고 적었으나 구현 전 코드 확인에서 사실이 아님을 확인해 정정, 2026-11-17)

**시드** `scripts/seed-stock-out-component-kinds.sql`: 구성 설정의 구성품이 이미 전부 대웅제약재고 품목이므로 다시 실행해도 아무 일도 하지 않는다. 헤더에 이번 변경 이후 상태를 적어 둔다.

## 8. 운영 유의 (D2 관련)

이관 직후에는 시스템 수량과 같은 병상 서버 수량이 같다. 이후에도 같으려면:

- **출고요청 처리**: 시스템 n개 출고 시 서버는 출고분 + 미출고분(운영팀재고 편입) 합쳐 n대가 대웅제약재고에서 빠지므로 **자동으로 맞는다**.
- **입고**: 시스템 수량 입고와 서버 시리얼 입고를 **각각** 해야 한다. 한쪽만 하면 어긋난다. 자동 연동은 이번 범위에 없다.
- **자재관리에서 직접 출고·조정**: 한쪽만 처리하면 어긋난다.

## 11. 보완 — 구성품 기록이 없는 요청 (2026-11-17, 사용자 dev2 확인에서 발견)

- **현상**: dev2에서 시스템100 1개 요청을 출고 처리하려니 서버(100병상) 시리얼 입력란이 나오지 않았다.
- **원인**: 구성품 행(`stock_out_request_components`)은 요청을 **저장할 때** 만들어진다. 2026-11-12 구성품 개편 전에 등록되고 그 뒤 다시 저장하지 않은 요청에는 행이 없다. 예전에는 시스템 라인이 시리얼을 받아 가려져 있었는데, 시스템이 수량 품목이 되자 이런 요청은 **서버 시리얼을 받는 칸이 전혀 없고 서버 재고도 빠지지 않게** 됐다. §3.4에서 '서버(워크스테이션)이 잡힌 요청'만 보고 '구성품이 아예 없는 요청'을 빠뜨렸다. dev2 5건(SOR-202611-0001·0006·0010·0012·0014). PROD는 같은 조건 0건(이미 전부 구성품이 있음 — 11-17 조회).
- **조치 ① 보정 스크립트** `scripts/backfill-stock-out-request-components.sql`(멱등, `-v finish=ROLLBACK|COMMIT`): 출고 처리 전·종결 전·분실 AS 연동 아님·구성품 0건이면서 시스템 라인이 있는 요청에, 현재 구성 설정으로 구성품 행을 채운다(미출고 0 — [수정]에서 그대로 저장한 것과 같음). **이관 스크립트 다음에 실행.**
- **조치 ② 출고 처리 가드**(`lib/stockOutFulfill.ts prepareFulfillment`): 구성품 행이 0건인데 현재 설정으로 계산하면 구성품이 나오는 요청은 전역 오류로 막는다 — "시스템 구성품이 계산돼 있지 않아 출고 처리할 수 없습니다. [수정]에서 그대로 저장하면 채워집니다." 시스템만 수량 차감되고 서버가 빠지는 일이 조용히 생기지 않게 한다.
- **PROD 반영 순서(§7 갱신)**: 코드 배포(마이그·가드) → 이관 스크립트 → 보정 스크립트(대상 0건이어도 실행해 확인).
