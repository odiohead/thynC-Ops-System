# thynC 사용량 수집 — 초기 버전 설계

> **상태: 구현 완료 (dev2, 2026-11-18) — dev 반영·병원 서버 시험 대기** (2026-11-17 작성 · 2차안, 2026-11-18 3차안·착수 승인·구현 — 구현 노트 §13)
>
> 범위: ① 병원 서버에 설치하는 Agent ② 원본 적재 스키마(별도 DB) ③ 수신부(별도 프로세스).
> 사용 구간 환산·지표 계산·조회 화면은 이번 범위가 아니다(§10).
>
> 2차안에서 바뀐 것: 누락분 재전송(§6) 신설 · 모든 원본 테이블에 병원 코드(§7.2) · 상태 이력 월별 분할(§7.3) · 수신 환경을 dev로(§9).
> 3차안(2026-11-18)에서 바뀐 것: 수신부를 본체와 별도 프로세스로(§8) · 원본을 본체와 별도 DB로(§7.4).

## 1. 이 기능이 답해야 할 질문

1. 병원 서버에서 지워지거나 덮어써지기 전에, 사용량 판단에 필요한 **사실**을 빠짐없이 가져왔는가
2. 가져온 사실이 **어느 병원** 것인지 분명한가
3. 나중에 세는 기준(하루를 넘기면 몇 건인지, 기기 교체를 1건으로 볼지 2건으로 볼지)을 바꿔도 **과거분까지 다시 계산**할 수 있는가
4. 전송이 한동안 끊겼어도 **빠진 것을 다시 받을 수 있는가**

세는 기준은 보려는 지표마다 다르므로 병원 서버에서는 계산하지 않는다. 병원은 사실만 보내고, 해석은 운영관리시스템이 한다.

## 3. 제품 DB에서 확인한 사실 (백엔드 소스 `01.01.442` 기준)

설계의 근거가 되는 것만 적는다.

- **측정 1건 = 환자 1명의 모니터링 1회** (`measurement_info` 1행). 기기를 여러 개 붙여도 측정 행은 1개이고 기기는 `device_info`에 여러 행으로 들어간다.
- **예외: 심전도 멀티리드.** 리드 1·3 기기를 붙이면 리드마다 자식 측정 행(`parent_type = 1`)이 생긴다.
- **측정 상태**: 1 대기 · 2 측정 중 · 3 종료 · 8 완료 · 10 삭제. DDL 주석(0~3)은 낡았다.
- **종료 시각**은 진행 중에도 비어 있지 않다. 시작 + 설정 기간으로 계산한 예정 시각이 들어 있다.
- **기기 교체**는 `device_info`의 같은 행을 덮어쓴다. 이전 기기는 `device_info`에서 즉시 사라진다.
- **기기 상태 이력**(`device_status_info_<연도>`)은 게이트웨이가 상태를 올릴 때마다 1행씩 추가된다. 번호(기본 키)가 순서대로 붙고 수정되지 않는다. 연도는 측정을 만든 해 기준이다.
- **보관 기한 삭제**: 종료 후 `global_setting.backup_day`(기본 90일)가 지난 측정은 측정 행만 상태 10으로 남고, 측정 기기·기기 상태 이력은 지워진다.
- **사용자 삭제**: 화면·관리자 삭제, 기한 지난 대기 측정 정리는 측정 행 자체를 지운다.
- **구독형 여부**는 `device_register.premium`이다. 기기 등록 때만 들어가고 값이 없으면 0이다.
- **측정코드**는 기관코드 + 생성 시각으로 만들어진다. 환자코드는 들어가지 않는다.
- 제품에 내장된 사용량 기능(`premium_connection_history`, 일별 전송)은 기록 누락이 구조적으로 생겨 쓰지 않는다.

확인하지 못한 것: 실제 서버의 보관 기한 값, 상태 이력의 하루 발생량, `message` 컬럼의 실제 내용, 게이트웨이가 상태를 보내는 빈도.

## 4. 전체 구조

```
[병원 서버]                                  [운영 서버]
 thync DB (MySQL, 조회 전용 계정)
     │ SELECT
 thync-usage-agent ── HTTPS(토큰) ──▶ Nginx ─ /api/usage-ingest/ ─▶ 수신부 프로세스
 (systemd 타이머, 실행 후 종료)                                        │ 전용 계정
                                                                      ▼
                                                                  원본 DB  (측정·기기·상태 이력)
                                                                      ▲ 읽기 (이후 단계: 지표 계산)
                                        Nginx ─ 그 외 경로 ─▶ 본체 앱 ─┘
                                                                └──▶ 본체 DB  (병원·기기 현황·AS, 이후 일별 지표)
```

- Agent는 밖으로 나가는 HTTPS만 쓴다. 포트를 열지 않고, 중앙에서 명령이나 쿼리를 받지 않고, 스스로 업데이트하지 않는다.
- 수신부는 받은 행을 지우지 않는다. 병원에서 사라진 것은 "사라짐" 표시만 한다.
- 병원 DB 자체가 전송 대기열 역할을 한다. Agent는 병원 서버에 따로 쌓아 두지 않는다.
- **수신부와 본체는 코드도 DB도 공유하지 않는다.** 수신부는 원본 DB만 알고, 본체 DB에는 접속 권한이 없다. 본체를 배포·재시작해도 수신은 끊기지 않는다.

## 5. Agent

### 5.1 형태

| 항목 | 내용 |
|---|---|
| 이름 | `thync-usage-agent` |
| 구현 | Go, 정적 빌드(linux/amd64), 외부 의존성은 MySQL 드라이버 1개 |
| 실행 | systemd 서비스(`Type=oneshot`) + 타이머. 1회 실행 후 종료 |
| 실행 계정 | 전용 시스템 계정 `thync-usage` (셸 없음, 쓰기 권한 없음) |
| 설정 | `/etc/thync-usage-agent/agent.env` (root 소유, 전용 계정만 읽기) |
| 로그 | 표준 출력 → journald (`journalctl -u thync-usage-agent`) |
| 소스 위치 | 이 레포 `agents/thync-usage-agent/` (수신 규격과 같은 저장소에서 관리) |

명령:

- `thync-usage-agent run` — 한 번 수집·전송한다 (타이머가 호출)
- `thync-usage-agent run --full` — 측정을 처음부터 전부 다시 보낸다 (§6.3)
- `thync-usage-agent run --status-from <번호>` — 상태 이력을 지정한 번호부터 다시 보낸다 (§6.3)
- `thync-usage-agent check` — DB 접속·중앙 접속·권한을 점검하고, 보낼 행 수만 보여 준다 (전송 없음)
- `thync-usage-agent version`

### 5.2 설정 항목

| 키 | 설명 | 기본값 |
|---|---|---|
| `USAGE_ENDPOINT` | 수신 주소 | (필수) |
| `USAGE_TOKEN` | 병원 토큰 | (필수) |
| `USAGE_SERVER_ID` | 이 서버의 이름 (병원 안에서 유일) | 호스트명 |
| `DB_HOST` / `DB_PORT` / `DB_NAME` | 제품 DB | `127.0.0.1` / `3306` / `thync` |
| `DB_USER` / `DB_PASSWORD` | 조회 전용 계정 | (필수) |
| `ORG_INCLUDE` | 보낼 기관코드 목록 (쉼표 구분). 비우면 전부 | 비어 있음 |
| `ORG_EXCLUDE` | 제외할 기관코드 | `REF_ORG` |
| `STATUS_BATCH_ROWS` | 상태 이력 1회 전송 행 수 | `5000` |
| `STATUS_MAX_BATCHES` | 1회 실행당 상태 이력 전송 횟수 상한 | `40` |

`ORG_INCLUDE`는 한 서버 DB에 여러 병원의 기관이 들어 있는 경우를 위한 것이다. 병원마다 설정 파일과 타이머를 하나씩 두고 기관코드로 나눈다.

### 5.3 한 번의 실행

1. 설정을 읽고 DB에 접속한다 (읽기 전용 세션).
2. 중앙에 시작을 알리고 이어 보낼 위치를 받는다 — 측정을 어느 시각 이후분부터 보낼지, 상태 이력을 연도별로 몇 번까지 받았는지, 오늘 대조를 할 차례인지.
3. 아래 데이터를 종류별로 조회해 보낸다.
4. 대조할 차례면 대조용 목록을 보내고, 중앙이 빠졌다고 알려 준 것을 다시 보낸다 (§6.2).
5. 결과(건수·소요 시간·오류)를 알리고 종료한다.

### 5.4 보내는 데이터

| 종류 | 원천 테이블 | 범위 | 주요 컬럼 |
|---|---|---|---|
| 기관 | `organization` | 전체 | 기관코드, 기관명, 유형, 등급, 만료 여부, 생성일 |
| 병동 | `ward` + `sickbed` 수 | 전체 | 기관코드, 병동코드, 병동명, 비활성 여부, 병상 수 |
| 기기 등록 | `device_register` | 전체 | 기관코드, 종류, 기기코드, 시리얼, 병동코드, 구독형 여부, 반납 상태, 누적 사용 시간·횟수, 등록일 |
| 측정 | `measurement_info` | 중앙이 알려 준 시각 이후 변동분 | 측정코드, 부모 측정코드, 부모/자식, 리드, 기관·병동·병실·병상 코드, 유형, 상태, 환자 상태, 시작·종료, 기간, 생성·수정 시각, 연도 |
| 측정 기기 | `device_info` (+ `device_register.premium`) | 위 측정에 붙은 기기 전부 | 기기 종류, 시리얼, 기기코드, 리드, 붙인 시각, 구독형 여부 |
| 기기 상태 이력 | `device_status_info_<연도>` | 받은 번호 이후 | 번호, 측정코드, 기기 종류, 시리얼, 상태, 배터리, 단말 종류, 시각 |
| 대조용 측정 목록 (하루 1회) | `measurement_info` | 전체 | 측정코드, 상태, 수정 시각 |
| 대조용 상태 이력 건수 (하루 1회) | `device_status_info_<연도>` | 지난 대조 이후 구간 | 구간의 시작·끝 번호, 행 수 |

- **측정의 변동분**: 진행 중(상태 2)이거나, 시작·종료·수정 시각 중 하나가 기준 시각 이후인 측정. 기준 시각은 "지난 성공 실행의 시작 시각 − 2일"이다. 첫 실행은 전체를 나눠 보낸다.
- **측정 기기는 측정 안에 묶어 보낸다.** 중앙은 측정마다 "지금 붙어 있는 기기 전체"를 받으므로, 빠진 기기를 알 수 있다.
- **시각은 변환하지 않는다.** DB에 있는 값 그대로(시간대 없는 문자열) 보내고, DB 시간대와 현재 시각을 실행 정보에 같이 보낸다.
- **조회 컬럼은 코드에 고정한다.** `SELECT *`를 쓰지 않고, 금지 컬럼(§2 D3)이 쿼리에 없음을 테스트로 확인한다.
- **상태 이력 테이블이 보이지 않으면 알린다.** 진행 중인 측정의 연도에 해당하는 상태 이력 테이블을 읽을 수 없으면(권한 누락 등) 실행 기록에 남기고 `check`는 실패로 표시한다.

초기 버전에서 보내지 않는 것:

- `device_status_info.message` — 자유 문자열이라 실제 내용을 확인하기 전까지 제외 (§11 Q2)
- MAC 주소 — 쓸 곳이 없음
- `premium_connection_history`, `premium_*` 테이블 — 기록이 부정확해 쓰지 않음
- 사용자 계정, 로그인 기록, 게이트웨이 — 사용량과 무관

### 5.5 병원 서버 보호

- DB 계정은 필요한 테이블에만 `SELECT` 권한을 준다 (`organization`, `ward`, `sickbed`, `device_register`, `measurement_info`, `device_info`, `device_status_info_*`, `global_setting`). 상태 이력은 연도별 테이블이라 2040년 테이블까지 미리 권한을 준다 — 해가 바뀌어도 병원 서버에서 할 일이 없다.
- 쿼리마다 실행 시간 상한을 둔다 (`MAX_EXECUTION_TIME`).
- 서비스는 낮은 우선순위로 실행한다 (`Nice=10`, `IOSchedulingClass=idle`).
- 상태 이력은 한 번에 정해진 행 수만 읽는다. 첫 실행에 쌓인 양이 많아도 여러 번에 나눠 따라잡는다.
- systemd 격리 옵션을 켠다 (`NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp`).

### 5.6 설치물

```
/opt/thync-usage-agent/thync-usage-agent        실행 파일
/etc/thync-usage-agent/agent.env                설정
/etc/systemd/system/thync-usage-agent.service   서비스
/etc/systemd/system/thync-usage-agent.timer     타이머
```

- `install.sh` — 계정 생성, 파일 배치, 설정 틀 생성, 타이머 등록
- `create-db-user.sql` — 조회 전용 DB 계정 생성
- `uninstall.sh`

타이머는 1시간 간격을 기본으로 한다 (`RandomizedDelaySec=10m`로 병원마다 시각을 흩고, `Persistent=true`로 꺼져 있던 동안 놓친 실행을 켜진 뒤 수행). 간격은 §11 Q1.

## 6. 누락 없이 받기 — 재전송

세 단계로 둔다. 앞의 둘은 사람이 개입하지 않는다.

### 6.1 자동 이어 보내기

- 어디까지 받았는지는 **중앙이 기억한다.** 병원 서버에는 상태 파일이 없다.
- 위치는 **저장에 성공한 뒤에만** 앞으로 간다. 전송 도중 끊기면 다음 실행이 같은 범위를 다시 보낸다.
- 모든 저장은 고유 키 기준 덮어쓰기라, 같은 행이 여러 번 와도 결과가 같다.
- Agent가 며칠 멈췄다가 살아나면 멈춘 시점부터 이어진다. 측정은 "지난 성공 실행 − 2일" 이후 변동분, 상태 이력은 받은 번호 다음부터다.

### 6.2 자동 대조 (하루 1회)

이어 보내기만으로는 빠진 것이 있어도 알 수 없으므로, 하루에 한 번 병원 쪽과 중앙 쪽을 맞춰 본다.

| 대상 | Agent가 보내는 것 | 중앙이 하는 일 |
|---|---|---|
| 측정 | 측정 전체의 목록 (측정코드·상태·수정 시각) | 중앙에 없거나 상태·수정 시각이 다른 측정코드를 응답 → Agent가 그 측정만 다시 보냄. 중앙에만 있는 측정은 "병원에서 사라짐"으로 표시 |
| 상태 이력 | 지난 대조 이후 구간의 시작·끝 번호와 행 수 | 같은 구간의 보유 행 수가 모자라면 수신 위치를 구간 시작으로 되돌림 → 다음 전송에서 다시 받음 |

- 측정 목록은 코드와 숫자뿐이라 작다. 한 번에 정해진 건수씩 나눠 보낸다.
- 이 대조가 병원에서 삭제된 측정을 찾는 수단이기도 하다.
- 중앙이 Agent에게 돌려주는 것은 측정코드 목록과 번호뿐이다. 쿼리나 명령을 보내지 않는다.

### 6.3 수동 재전송

- **중앙에서**: 병원·서버를 지정해 수신 위치를 되돌린다 (`scripts/usage-rewind.mts`). 다음 실행 때 그 지점부터 다시 들어온다. 병원 서버에 접속할 필요가 없다.
- **현장에서**: `thync-usage-agent run --full`(측정 전체), `run --status-from <번호>`(상태 이력).

### 6.4 한계

**병원 DB에서 이미 지워진 것은 다시 보낼 수 없다.** 보관 기한(기본 90일)보다 오래 전송이 끊기면 그사이 종료된 측정의 기기 정보와 상태 이력은 잃는다. 그래서 장기 미수신을 찾을 수 있어야 한다.

- 서버별 마지막 성공 시각을 기록한다 (`agent_servers.last_success_at`).
- 초기 버전에서는 조회 스크립트로 확인한다 (`scripts/usage-status.mts` — 병원·서버별 마지막 수신, 밀린 양, Agent 버전). 알림은 다음 단계다.

## 7. 원본 적재 스키마

본체 DB와 별개의 **원본 DB**를 둔다 (§7.4). 아래 테이블은 모두 원본 DB에 있고, 본체 DB의 테이블을 참조하지 않는다.

### 7.1 식별 — 병원, 그 아래 서버

**`agent_tokens`** — 병원 토큰

| 컬럼 | 설명 |
|---|---|
| `id` | |
| `hospital_code` | 본체의 병원 코드 (`HOSP-…`). DB가 달라 참조 제약은 없고, 토큰을 발급할 때 본체 DB에 있는 병원인지 확인한다 |
| `token_hash` | 토큰의 SHA-256 (원문은 저장하지 않음), UNIQUE |
| `token_prefix` | 앞 8자 (목록 표시·문의 대응용) |
| `label` | 메모 |
| `active` | |
| `created_by`, `created_at`, `revoked_at`, `last_used_at` | |

토큰은 병원에 속한다. 병원의 서버들은 같은 토큰을 쓴다. 교체할 때 끊기지 않도록 한 병원에 활성 토큰을 2개까지 허용한다.

**`agent_servers`** — 병원의 서버 (첫 접속 때 자동 등록)

| 컬럼 | 설명 |
|---|---|
| `id` | |
| `hospital_code` | |
| `server_id` | Agent가 보낸 서버 이름. `(hospital_code, server_id)` UNIQUE |
| `hostname`, `agent_version`, `db_version`, `db_time_zone` | 마지막 접속 때 값 |
| `first_seen_at`, `last_seen_at`, `last_success_at` | |
| `measurements_synced_until` | 측정을 어디까지 받았는지 |
| `reconciled_at` | 마지막 대조 시각 |

본체 DB의 `hospital_servers`(사람이 입력하는 서버 현황 카드)와는 합치지 않는다. 그쪽은 설명 정보이고 이쪽은 기계가 보고하는 값이다.

**`agent_runs`** — 실행 이력: 병원, 서버, 시작·종료 시각, 상태(진행 중/성공/실패), Agent 버전, 종류별 건수(JSON), 대조 결과(JSON), 오류 내용, 접속 IP.

**`status_cursors`** — 상태 이력 수신 위치: `(server, table_year)` → 받은 번호 `last_id`, 대조를 마친 번호 `verified_id`

### 7.2 원본 테이블

**모든 원본 테이블에 `hospital_code`를 둔다** (NOT NULL). 어느 병원 데이터인지는 이 컬럼 하나로 구분하고, 조회·집계·삭제의 기준도 이 컬럼이다. 인덱스는 `hospital_code`로 시작한다.

`server`(→ `agent_servers.id`)는 그 아래 구분이다. 고유 키에는 서버까지 넣는다. 같은 병원의 서버 두 대가 같은 코드나 같은 번호를 쓰는 경우에도 섞이지 않게 하기 위해서다.

공통 컬럼: `hospital_code`, `server`, `first_seen_at`, `last_seen_at`.

| 테이블 | 고유 키 (모두 서버 포함) | 내용 | 병원에서 사라졌을 때 |
|---|---|---|---|
| `raw_organizations` | 기관코드 | 기관명, 유형, 등급, 만료 여부, 생성일 | `gone_at` 기록 |
| `raw_wards` | 병동코드 | 기관코드, 병동명, 비활성 여부, 병상 수 | `gone_at` 기록 |
| `raw_device_registers` | 시리얼 | 기관코드, 종류, 기기코드, 병동코드, 구독형 여부, 반납 상태, 누적 사용 시간·횟수, 등록일 | `gone_at` 기록 |
| `raw_measurements` | 측정코드 | §5.4 측정 컬럼 전부 | `source_gone_at` 기록 |
| `raw_measurement_devices` | 측정코드 + 기기 종류 + 시리얼 | 원본 행 번호, 기기코드, 리드, 붙인 시각, 구독형 여부 | `removed_at` 기록 |
| `raw_device_status` | 연도 + 원본 번호 (+ 발생 시각) | 측정코드, 기기 종류, 시리얼, 상태, 배터리, 단말 종류, 발생 시각, 수신 시각 | (추가만 됨) |

설계 판단:

- **기기 교체가 남는다.** `raw_measurement_devices`의 키에 시리얼이 들어 있어서, 병원 DB에서 시리얼이 덮어써지면 중앙에는 새 행이 생기고 이전 행은 `removed_at`만 찍힌 채 남는다.
- **구독형 여부를 두 곳에 둔다.** 기기 등록(현재 값)과 측정 기기(그 측정이 전송되던 시점의 값). 나중에 기기의 구독형 값이 바뀌어도 과거 측정의 구분이 따라 바뀌지 않게 하기 위해서다.
- **시각은 시간대 없는 값으로 저장한다.** 병원 DB의 값 그대로이고, 시간대는 서버 정보(`db_time_zone`)에 있다.
- **보관 기한이 지나 상태 10으로 바뀐 측정**은 변동분으로 다시 들어온다. 이때 중앙은 측정의 상태만 갱신하고, 이미 받아 둔 측정 기기와 상태 이력은 건드리지 않는다.
- **`hospital_code`에는 토큰에서 정해진 값만 들어간다.** 요청 본문에 병원 코드가 있어도 쓰지 않는다. 참조 제약이 없어도 잘못된 병원 코드가 들어올 경로가 없다.
- **병원 코드가 바뀌는 경우**(중복 병원 정리)는 원본 DB의 병원 코드도 따로 바꿔야 한다. 병원 정리 절차에 한 줄 추가하고, 바꾸는 스크립트를 둔다 (`scripts/usage-move-hospital.mts`).

주요 인덱스:

- `raw_measurements`: `(hospital_code, start_at)`, `(hospital_code, end_at)`, `(hospital_code, measurement_status)`
- `raw_measurement_devices`: `(hospital_code, serial_number)`
- `raw_device_status`: `(hospital_code, measurement_code, event_at)`

### 7.3 단일 테이블인가, 나누는가

나누는 방법은 세 가지다.

| 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 병원별 테이블 | 병원 하나를 통째로 떼기 쉬움 | 테이블이 병원 수만큼 늘고, 컬럼 하나 바꾸려면 전부 고쳐야 함. 전 병원 집계가 어려움. 제품 DB가 이 방식이라 테이블이 1,800개가 됨 | 채택하지 않음 |
| 단일 테이블 + 병원 코드 인덱스 | 가장 단순. 병원별 조회는 인덱스로 충분 | 행이 수억 개가 되면 오래된 데이터를 덜어내기 어려움 | 작은 테이블에 채택 |
| 기간별 분할 (한 테이블, 내부적으로 월 단위 조각) | 겉으로는 한 테이블. 오래된 달을 조각째 떼어 보관하거나 지울 수 있음 | 고유 키에 분할 기준 시각이 들어가야 하고, 달마다 조각을 만들어야 함 | 상태 이력에 채택 |

테이블별 결정:

| 테이블 | 예상 규모 | 형태 |
|---|---|---|
| 기관, 병동, 기기 등록 | 전 병원 합쳐 수만 행 | 단일 테이블 |
| 측정, 측정 기기 | 전 병원 합쳐 연 수백만 행 수준 (추정) | 단일 테이블. 수년간 문제없는 크기 |
| **기기 상태 이력** | 미확인. 아래 표 | **처음부터 월별 분할** |

상태 이력만 처음부터 나누는 이유는, 끝없이 쌓이는 유일한 테이블이고 수억 행이 된 뒤에 나누는 작업은 훨씬 어렵기 때문이다. 분할 기준은 발생 시각(`event_at`)의 달이다. 같은 원본 행은 발생 시각이 항상 같으므로 다시 받아도 같은 조각에서 덮어써진다. 달 조각은 수신할 때 없으면 만든다.

상태 이력의 연간 크기 추정 (행당 약 224바이트 — dev2에서 20만 행을 넣어 실측한 값으로, 데이터 104 + 인덱스 120. 150개 병원 가정):

| 병원당 하루 발생량 | 연간 행 수 | 연간 크기 |
|---|---|---|
| 1,000행 | 약 5,500만 | 약 12GB |
| 10,000행 | 약 5억 5천만 | 약 120GB |
| 50,000행 | 약 27억 | 약 610GB |

하루 발생량은 상용 서버 샘플로 확인해야 한다. 양이 많은 쪽이면 "원본 상태 이력은 일정 기간만 DB에 두고, 지난 달 조각은 S3로 옮긴다"가 필요하고, 월별 분할이 그 전제다. 병원별 분할은 하지 않는다. 병원별 조회는 인덱스로 처리된다.

### 7.4 원본 DB를 본체와 분리한다

| 환경 | 본체 DB | 원본 DB |
|---|---|---|
| dev2, dev | `thync_ops_dev` | `thync_usage_dev` |
| PROD | `thync_ops` | `thync_usage` |

분리하는 이유:

- **크기가 다르다.** 본체 DB는 덤프가 수십 MB인데, 원본 상태 이력은 연 수 GB에서 수백 GB까지 나올 수 있다. 같은 DB에 두면 일일 백업, PROD → DEV 데이터 동기화, 비상 복구가 전부 이 크기에 끌려간다.
- **성격이 다르다.** 본체는 고쳐 쓰는 업무 데이터이고, 원본은 쌓기만 하는 기록이다. 백업 주기·보관 기간·복구 우선순위가 다르다.
- **기존 절차를 건드리지 않는다.** DB가 따로이므로 본체의 백업 스크립트, 동기화 스크립트, 비상 복구 절차는 그대로다.
- **옮기기 쉽다.** 다른 서버로 옮길 때 원본 DB만 덤프해서 올리고 접속 주소를 바꾸면 된다.

단계:

| | 1단계 — 같은 PostgreSQL 안의 별도 DB (지금) | 2단계 — 별도 서버의 DB |
|---|---|---|
| 백업·동기화·복구 분리 | 됨 | 됨 |
| 권한 분리 | 됨 | 됨 |
| 디스크·부하 분리 | 안 됨 | 됨 |

1단계로 시작한다. 상태 이력의 실제 양이 연 수십 GB 이상으로 확인되면 2단계로 옮긴다. 1단계에서는 디스크가 공유되므로 용량 안전장치(§8)가 필요하다.

접속 계정:

- 원본 DB 전용 계정 `thync_usage`를 만든다. 원본 DB의 소유 계정이고, 본체 DB에는 권한이 없다.
- 수신부는 이 계정만 쓴다. 수신부의 설정 파일에는 본체 DB의 접속 정보가 없다.
- 본체 쪽 스크립트(§8)와 이후의 지표 계산은 본체 `.env`의 `USAGE_DATABASE_URL`로 원본 DB에 접속한다.

스키마 관리:

- 본체의 Prisma와 별개다. 번호가 붙은 SQL 파일(`usage-ingest/migrations/0001_….sql`)과 적용 기록 테이블(`schema_migrations`)로 관리하고, 적용은 스크립트 한 번으로 한다.
- 원본 DB에는 Prisma 모델을 만들지 않는다. 수신부와 스크립트는 SQL을 직접 쓴다.

분리의 비용:

- 지표 계산 작업이 DB 두 곳에 접속한다 (원본에서 읽고 본체에 쓴다).
- 한 쿼리로 원본과 병원 정보를 조인할 수 없다.
- 환경마다 DB와 계정을 하나씩 더 만든다. dev·PROD 서버의 PostgreSQL에 DB를 만드는 것은 서버 작업이라 명시 허락을 받고 한다.

**원본 DB의 백업**: 병원에서 지워진 뒤에는 원본 DB가 유일한 사본이다. dev 시험 단계에서는 백업 없이 진행하고, PROD에 올리기 전에 백업 방식을 정한다 (작은 테이블은 매일 전체, 상태 이력은 달 조각 단위). 기존 S3 백업 스크립트의 검증·업로드 부분을 다시 쓸 수 있다.

| 설정 | `usage-ingest/.env` (본체 `.env`와 별개) — `USAGE_DATABASE_URL`, `USAGE_INGEST_PORT`, `USAGE_MAX_BYTES` |
| 새 패키지 | `pg` (PostgreSQL 접속) 1개 |
| 상태 확인 | `GET /api/usage-ingest/health` — 버전, DB 접속 여부 (인증 없음) |

- **Nginx에서 `/api/usage-ingest/` 경로만 수신부로 넘긴다.** Agent가 보는 주소는 본체와 같은 도메인이고, 본체 앱은 이 경로를 받지 않는다. 그래서 본체의 미들웨어는 고치지 않는다.
- **빌드와 재시작은 수신부 코드가 바뀐 배포에서만 한다.** `usage-ingest/`가 바뀌었으면 `npm run build:usage-ingest` → `pm2 restart thync-usage-ingest-<환경>`. 본체만 바뀐 배포에서는 수신부를 빌드하지도 재시작하지도 않는다. 빌드는 1초 안에 끝난다.
- 재시작하는 몇 초 동안 들어온 전송은 실패하고, Agent가 다음 실행 때 다시 보낸다.

### 8.2 호출

경로는 `/api/usage-ingest/v1/`이다.

| 호출 | 요청 | 응답 |
|---|---|---|
| `POST /handshake` | 서버 이름, 호스트명, Agent 버전, DB 버전·시간대·현재 시각, 있는 상태 이력 연도 목록 | 실행 번호, 측정 기준 시각(없으면 전체), 연도별 받은 번호, 대조할 차례 여부, 전송 상한, 상태 이력 수신 중지 여부 |
| `POST /push` | 실행 번호, 종류, 행 목록 (상태 이력은 연도 포함) | 받은 행 수, (상태 이력) 갱신된 번호, (대조용 목록) 다시 보낼 측정코드 |
| `POST /finish` | 실행 번호, 결과, 종류별 건수, 오류 내용 | 확인 |

- **인증**: `Authorization: Bearer <토큰>` → 해시로 조회 → 병원 확정. 요청 본문의 병원 정보는 믿지 않는다.
- **본문**: JSON, gzip 압축. 요청당 행 수와 크기에 상한을 둔다.
- **멱등**: 모든 저장은 고유 키 기준 덮어쓰기다.
- **빈도 제한**: 토큰별·IP별.
- **성공 처리**: `finish`가 성공으로 오면 `measurements_synced_until`을 이번 실행의 시작 시각으로 올린다. 실패하면 올리지 않는다.
- **용량 안전장치**: 원본 DB 크기가 환경별 상한(`USAGE_MAX_BYTES`)을 넘으면 상태 이력 수신을 멈춘다. `handshake`가 중지 여부를 알려 주고, Agent는 상태 이력만 건너뛴다. 측정 등 작은 데이터는 계속 받는다. 멈춘 동안의 상태 이력은 병원 DB에 그대로 있으므로 상한을 풀면 이어서 들어온다.
- **Agent는 HTTPS 주소만 받는다.** 로컬 검증을 위해 `localhost`만 예외로 한다.

### 8.3 본체 쪽 스크립트

초기 버전에서는 화면 없이 스크립트로 한다. 본체 레포의 `scripts/`에 두고, 본체 `.env`의 `USAGE_DATABASE_URL`로 원본 DB에 접속한다.

- `scripts/usage-issue-token.mts <병원코드> [메모]` — 토큰 발급. 본체 DB에 있는 병원인지 확인하고, 토큰 원문을 한 번만 출력한다
- `scripts/usage-status.mts` — 병원·서버별 수신 현황 (마지막 수신, 밀린 양, Agent 버전, 원본 DB 크기)
- `scripts/usage-rewind.mts` — 수신 위치 되돌리기
- `scripts/usage-move-hospital.mts` — 병원 코드 변경 반영

- **토큰은 환경마다 따로 발급한다.** dev에서 발급한 토큰은 PROD에서 통하지 않는다.
- **수신 주소가 시험과 운영에서 다르다.** Agent 설정의 `USAGE_ENDPOINT`와 `USAGE_TOKEN`을 함께 바꾸면 전환된다. 운영 수신부는 그 병원을 처음 보는 것으로 취급해 처음부터 전부 받는다. 병원 방화벽이 목적지 주소를 지정해 열리는 경우, 전 병원에 설치하기 전에 운영 수신 주소를 확정해야 한다.

### 13.2 설계에서 달라지거나 구체화된 것

- **"사라짐" 표시의 안전장치.** Agent 쪽 문제(권한 누락, 기관 설정 실수)로 목록이 비정상적으로 작게 올 수 있다. 측정 대조에서 목록이 비었거나 받아 둔 측정의 절반 넘게(100건 초과) 사라진 것으로 나오면 표시하지 않고 실행 기록에만 남긴다. 기관·병동·기기 등록도 그 실행에서 한 건도 오지 않았으면 표시하지 않는다.
- **측정 대조가 실제로 맡는 범위.** 진행 중인 측정은 매 실행마다 변동분으로 다시 오므로 빠져도 다음 실행에 스스로 돌아온다. 대조가 없으면 돌아오지 않는 것은 오래전에 끝난 측정과 병원에서 삭제된 측정이다.
- **상태 이력 대조는 "대조를 마친 번호" 이후 구간만 센다.** 한 번 맞춰 본 구간은 다시 세지 않는다. 이미 맞춰 본 구간이 중앙에서 나중에 손실된 경우는 수동 되돌리기(`usage-rewind --status=…`)로 다시 받는다.
- **아직 없는 연도 테이블의 조회 권한.** MySQL은 없는 테이블에 `SELECT`만 줄 수 없다. `CREATE`와 함께 준 뒤 `CREATE`를 바로 거두면 `SELECT`만 남는 것을 dev2 MySQL 8.0.46에서 확인했고, 이 방식으로 2040년까지 미리 준다.
- **Agent의 재시도.** 연결 실패·5xx·429는 2초·5초·15초 간격으로 세 번 더 시도하고, 그 밖의 4xx는 바로 실패한다.
- **겹쳐 실행되는 경우.** 타이머 실행 중에 누군가 수동으로 `run`을 하면, 수신부가 앞선 실행을 실패로 닫고 뒤의 실행만 받는다. Agent 쪽 잠금 파일은 두지 않았다(쓰기 권한이 없는 계정).
- **기준 시각의 여유 2일.** 측정의 수정 시각은 제품 앱이 넣는 값이라 DB 시각과 시간대가 다를 가능성이 있다. 변동분 기준에서 2일을 빼는 것과 하루 한 번의 대조가 이 차이를 덮는다.

### 13.3 dev2 검증 결과

- **끝단 검증 `scripts/usage-collect-smoke.mts` 93/93** (연속 2회). 로컬 MySQL의 빈 제품 DB에 가상 데이터를 넣고 실제 Agent 실행 파일 → 수신부(PM2) → 원본 DB를 돌린다.
  - 첫 실행 전체 수신, 다시 실행해도 같은 결과
  - 환자 식별 정보: 가상 측정에 이름·환자코드·주민번호·연락처·주소·생년월일·메모·MAC을 넣어 두고, 원본 DB 전체에 그 값이 없음을 확인. 조회 전용 계정은 환자 테이블을 읽지 못하고 쓰지 못함
  - 기기 교체(이전 기기 행이 남음), 측정 종료, 보관 기한 삭제(기기·상태 이력 유지), 병원에서 삭제된 측정(표시만)
  - 누락 복구: 오래된 측정은 대조로, 상태 이력은 행 수 대조 → 위치 되돌림 → 다음 실행에 복구
  - 수동 재전송(중앙 되돌리기, 현장 옵션), 전송 상한에서 멈춤·이어 보내기, 수신부 정지 중 실패 후 재개, 잘못된 토큰
  - 용량 상한 도달 시 상태 이력만 중지, 상한 해제 후 이어서 수신
  - 같은 병원의 두 번째 서버, 기관 지정, 다른 병원 토큰, 다른 병원의 실행 번호 사용 불가
  - 수신부 요청 검사 13종, 운영 스크립트 4종
- **Agent 단위 테스트**: 모든 쿼리에 금지 컬럼·`SELECT *`·쓰기 문장이 없음, 설정 해석, 기관 조건.
- **systemd 설치**: 설치 묶음으로 dev2에 설치 → 전용 계정으로 `check` 통과 → `systemctl start`로 1회 실행 성공(격리 옵션 적용 상태) → 타이머 등록 → `uninstall.sh --purge`로 제거.
- **실측**: 상태 이력 20만 행(1회 실행 상한)을 2.2초에 전송. Agent CPU 0.7초, 최대 메모리 5.5MB. 원본 DB 저장은 행당 224바이트. 수신부 메모리는 평소 25MB, 대량 수신 직후 약 100MB.

### 13.4 아직 확인하지 못한 것

- **실제 병원 DB에서의 동작.** 쿼리는 제품 초기 구성 SQL로 만든 빈 DB에서만 돌렸다. 실제 서버의 테이블 정의가 다르거나 데이터가 예상과 다르면 `check`에서 드러난다.
- **상태 이력의 실제 양과 `message` 내용.** 병원 서버에서 `check`를 돌리면 남은 행 수가 나온다.
- **Nginx 경유.** dev2에서는 Agent가 수신부에 직접 붙었다. 본문 크기 제한과 `X-Real-IP` 전달은 dev에서 확인한다.
- **병원 서버의 외부 통신.** 설계 전부터의 전제이고, 여전히 병원별로 확인해야 한다.

### 13.5 dev에 올릴 때 (요청 시)

dev 서버(13.125.238.77)에서 한다. 서버 설정 변경이 포함되므로 명시 허락을 받고 진행한다.

1. 원본 DB와 계정 생성: `thync_usage_dev`, `thync_usage` (PostgreSQL 관리자 권한)
2. `git pull` → `npm install` → `npm run build:usage-ingest` (본체 빌드는 이번 변경과 무관)
3. `usage-ingest/.env` 작성 (`.env.example` 참고) → `node usage-ingest/dist/migrate.mjs`
4. `pm2 start usage-ingest/dist/index.mjs --name thync-usage-ingest-dev --time` → `pm2 save`
5. Nginx `dev.ops` 설정에 `/api/usage-ingest/` 경로를 `127.0.0.1:3110`으로 넘기는 블록 추가 (본문 크기 제한, `X-Real-IP` 전달 포함) → 설정 검사 후 다시 읽기
6. 본체 `.env`에 `USAGE_DATABASE_URL` 추가 → `npx tsx scripts/usage-issue-token.mts <병원코드>`로 토큰 발급
7. 병원 서버: 설치 묶음 복사 → `install.sh` → `create-db-user.sql` → `agent.env` → `check` → 타이머 켜기
