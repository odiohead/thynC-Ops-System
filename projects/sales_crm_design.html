1. 배경·목표

운영관리시스템 1.0은 운영 실무(task) 데이터를 축적해 왔다. 이번 개발은 새 업무 모듈이 아니라 영업(Sales/CRM) 정보 축을 시스템에 추가하는 것이다. 중심은 병원(hospitals)이며, 핵심은 데이터 모델 — UI는 각 Phase에서 화면을 보며 확정한다.

v2 보완 관점 (사용자 피드백 반영)

  1. 매출은 차수(1차·2차·N차) 단위 — 한 병원에 도입이 여러 번. 차수별 가격 + 병원 전체 매출(합계) 둘 다 필요
  2. 웨어러블 디바이스 종별 수량 — 어떤 디바이스가 몇 개씩 들어갔는지 차수별·병원별 파악
  3. 대웅 관리체계(사업소·담당자)는 필수 아님 — 병원 마스터의 하위 테이블로 분리 (본체에 FK 안 심음)
  4. 영업일지 — 구조화 테이블 vs 병원노트(위키) 비교·추천 (§5.5)

3. 설계 원칙

  1. 운영 축과 분리, 연결로 통합 — 영업 데이터는 별도 테이블군, 기존 테이블 컬럼 추가 없음
  2. 병원 = 마스터, 영업 정보 = 하위 테이블 — 프로필(1:1)·키맨·대웅 채널·딜·영업일지(각 1:N) 전부 hospitals 하위. 필수 입력 없음 — 아는 만큼만 쌓는다
  3. 일정·상태의 단일 소스는 운영 축 — 중복 저장 금지, 조인 표시
  4. 금액·계약의 단일 소스는 딜 — 병원 총매출·디바이스 총수량은 전부 딜 합산 파생값 (별도 저장 금지)
  5. 마스터 코드화 — 판매가유형·정산·매출인식 등은 StatusCode 신규 카테고리
  6. 티켓 미편입 — 영업 정보는 task가 아님 (티켓·Slack·SLA 대상 아님)
  7. 민감정보 권한 게이트 — 매출 금액 열람 권한은 좁게 시작 (§6)
  8. 비소급·안전 마이그레이션 — 순수 추가 DDL, 기존 화면 무변경
