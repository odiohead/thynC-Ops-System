1.이 문서의 성격 · v1에서 무엇이 바뀌었나

이 문서는 기획안입니다. "무엇을, 왜 만들 가치가 있는가"를 다루고, 테이블·API·화면 설계는 다루지 않습니다. 각 항목은 방향이 선택된 뒤 별도 설계안(projects/*_design.md)을 작성하고 검토·승인을 거쳐야 착수합니다(기존 설계 게이트 그대로).

v1(8월 2일)과의 차이 세 가지
  • 진단 데이터가 바뀌었습니다. v1은 PROD 7월 31일 동기화본 기준이었고, 그 뒤 3개월 동안 디바이스 원장(기기 30,206대), AS 도메인(접수 4,301건), 채널톡 적재·VOC 자동 승격(VOC 10,708건), 출고업무 v2, 모바일 PWA v1이 출시됐습니다. v1의 "설치 기반 공백" 신호는 해소됐고, 대신 장부의 정확도를 사람이 손으로 지키고 있다는 새 신호가 나타났습니다.
  • 이용 패턴이 확인됐습니다. 최근 30일 감사 로그 12,879건 중 74%가 AS 처리입니다. 티켓의 83%가 VOC·AS입니다. 시스템의 무게중심이 '기록'에서 'CS·AS 운영'으로 이동한 것이 데이터로 확인됩니다.
  • Wave를 재편했습니다. v1 Wave 1의 A1(장비 개체)은 완료됐고, 그 자리에 "원장 정확도 운영(A1′)·AS 분석(A4)·운영 셀프서비스(F5)·인프라(F4)"가 들어옵니다. 반복 매출(B)은 여전히 본론이지만, 딜 데이터 보강(필수 필드·첨부·도입형태 보정)으로 착수 조건이 v1보다 좋아졌습니다.

3.2 이용 패턴 — 무엇이 실제로 쓰이는가

  • AS가 시스템 활동의 중심입니다. 운영팀 24명이 하루 평균 300건 이상의 AS 처리 액션을 남깁니다. AS 접수→종결 중앙값 8일, 평균 10일(최근 1,772건). 상위 10개 병원이 AS의 25%를 차지합니다(174개 병원 중).
  • CS 인입은 채널톡 한 줄기로 모였습니다. 수기 VOC 등록은 사라지고 자동 승격이 기본이 됐습니다. 즉 "입력"은 거의 자동화됐고, 병목은 "읽고 판단하는" 쪽입니다. 현재 읽는 도구는 주간 대시보드 1개입니다.
  • 장부는 생겼지만 사람 손으로 지키고 있습니다. 9~11월 DEV_HISTORY에 "[운영 데이터 조치]·보정" 항목이 28건입니다. 시리얼 오타 정정, 교체↔수리반환 정정, 라이트 딜 기기 일괄 등록, 분실 라인 보정 등 — 전부 개발자가 SQL·스크립트로 처리했습니다.
  • 현장 도구 수요가 실증됐습니다. 모바일 PWA v1 출시 직후 주차등록 343건/30일, 출고요청 모바일 등록 시작. 바코드 스캔 기반은 깔렸습니다.
  • 인프라가 성장 속도를 못 따라갑니다. PROD는 t3.medium(2 vCPU·3.8GB)에 PROD·DEV·협업 서버·DB가 동거합니다. 11월 3일 디스크 100%로 빌드 실패, 빌드마다 스왑 2GB, DEV 빌드 중 load 15. 인스턴스 이전이 논의 중입니다.

6.2 추천 Wave (순서의 논리)

Wave 0 — 바닥 정비 (즉시, 1개월)
F4 인프라(인스턴스·DEV 분리·빌드 분리) → E1 정합성 규칙 1차(5~6개 규칙 + 큐 화면) → F5 셀프서비스 상위 5종.

Wave 1 — 읽는 도구 (2~3개월)
A4 AS 분석 → E4 통합 검색 → E2 KPI 뼈대(주간 대시보드·영업 대시보드 통합) → A1′ 원장 정확도(WMS 대조부터).
논리: 입력은 자동화됐고(채널톡·원장), 운영팀 24명이 하루 300건을 처리합니다. 다음 병목은 "판단"이고, 가장 빨리 체감되는 건 AS 분석입니다.
Wave 2 — 돈 흐름과 예방 (2.0의 본론, 분기 단위)
B2 계약 달력 → B1 정산 원장(Wave 1 기간 중 도메인 확인 완료 조건) → A2 PM + D1 디스패치(짝) → D4 모바일 2.0.
논리: v1과 같습니다. 다만 B2는 딜 데이터 정비로 바로 시작할 수 있고, D4는 PWA v1이 있어 v1 때보다 가볍습니다.
Wave 3 — 고객 접점과 지능화 (차별화)
C3 운영 리포트 → E3 AI 부조종사(읽기 보조부터) → C2 건강도 → C1 포털 파일럿(또는 채널톡 안 셀프조회).
상시 트랙: F1 어휘 동기화(Wave 0~1에 걸쳐 조금씩) · F3 규제 조사 · A3 텔레메트리 대화.

7.전제 · 리스크 · 결정 필요 항목

7.1 전제

  • 1.0+의 티켓·원장·채널톡 파이프라인은 재설계하지 않고 그 위에 얹는다.
  • 각 항목은 기획 → 설계안 → 검토·승인 → 구현의 게이트를 그대로 거친다. 이 문서는 어떤 항목의 착수 승인도 아니다.
  • 숫자는 PROD 2026-11-06 실측(부록)이며, 로그인 활동·AS 리드타임·부서 분포는 dev2 10-29 동기화본이다.

7.2 주요 리스크

리스크내용완화
장부 신뢰E2·C2·A4의 숫자가 틀리면 신뢰를 잃는다. 원장은 아직 수동 보정 중E1을 항상 선행. 분석 화면마다 "정합성 미확인 n건" 배지
B1 도메인정산 실무·요율·대웅 분담이 시스템 밖 지식Wave 1 기간에 인터뷰·요율 실사. 확인 전 B1 착수 금지
운영 부하운영팀이 AS 처리에 묶여 새 도구 적응 여력이 적다읽는 도구(A4·E4)는 입력 추가 없이 기존 데이터만 사용. 입력을 늘리는 항목(A2·D2)은 Wave 2 이후
인프라지금 서버에서는 Wave 1 수준의 배포 빈도도 위험F4를 Wave 0으로 고정
범위 팽창22항목이 동시에 열리면 설계 게이트가 형식화된다Wave당 동시 진행 2~3항목 제한

7.3 사용자 결정이 필요한 것 (기획 단계)

  1. 2.0의 중심 — 추천은 "신뢰 가능한 장부 + AS 지능"(E1·A1′·A4)을 먼저, 그 다음 반복 매출(B). 회사 우선순위(예: 라이트형 확대로 B가 급하다면)에 따라 Wave 1·2 교체 가능.
  2. 인프라 투자 — 인스턴스 증설(t3.large/xlarge) vs 신규 이전, DEV 분리 여부. Wave 0의 첫 결정.
  3. B1 실현 가능성 확인 주체 — 정산 실무(사용량 원천·요율·대웅 역할)를 누가, 언제 확인하는가.
  4. 고객 접점 형태 — 포털(C1) vs 채널톡 안 셀프조회. 포털이면 F2 외부 계정 모델이 선행.
  5. 모바일 범위 — D4를 운영팀 현장 도구로 한정할지, 영업(출고요청·방문 기록)까지 넓힐지.
  6. 대웅과의 데이터 교환 — F1 어휘 동기화를 위해 대웅 측 품목·거래처·디바이스 자료의 정기 수령 경로를 합의할 수 있는지.
