1. 배경과 목표

1.1 요구사항

#요구사항
R1Slack을 메인 핵심 알림체계로 가져가지 않는다
R2시스템 안에서 본인 계정 알림 확인
R3궁극 목표는 별도 페이저 앱 — 이번 범위 아님
R4SLA가 지난 그 시점에 특정 채널 알림
R5SLA 지난 전체 리스트를 하루 한 번 특정 시각에 채널 알림
R6특정 티켓 유형의 생성·상태 변경 시 특정 채널 알림
R7유형도 여러 개, 채널도 여러 개 — 상황별 제어
R8첫 화면 개인화 — 기본 대시보드 + 나의 티켓 현황
R9SLA 지난 티켓을 시스템 안에서 인지
R10SLA 세분화 — 등급×생성→완료 단일 측정은 부족. 장기 프로젝트, CS의 "몇 시간째 미배정" 축 필요 + 세밀한 커스터마이징

1.2 설계 원칙 전환 (이번 개선의 핵심)

1.0은 “알림 = Slack 발송 행위”였다. 시스템 안에는 사용자가 볼 알림이 존재하지 않는다. 1.1은 이 관계를 뒤집는다.

[1.0]  티켓 이벤트 ──▶ Slack 발송 ──▶ notification_logs (발송 감사 기록)
                                       └ 사용자가 볼 알림은 시스템에 없음

[1.1]  티켓 이벤트 ──▶ 알림 레코드(notifications) ─┬─▶ 시스템 내부 알림함·벨·첫 화면
       SLA 시계 초과 ──┘                          ├─▶ Slack 채널 어댑터 (라우팅 규칙)
                                                  └─▶ (향후) 페이저 앱 푸시
  • 알림의 원본은 DB, Slack은 밖으로 내보내는 어댑터 하나로 격하 R1
  • 이 구조가 곧 페이저 앱의 전제 — 푸시 대상이 사용자별로 DB에 쌓여 있어야 앱을 붙일 수 있다 R3
  • SLA는 “시계(clock)” 1급 개념으로 승격 — 티켓 하나가 여러 시계를 동시에 갖는다 R10

2. 현재 형상 진단 (코드 근거)

2.1 Slack 알림 — 되는 것과 안 되는 것

항목현재근거
이벤트 발송티켓 생성·상태변경·큐이관·Sev 에스컬레이션lib/notify.ts
변경 감지sig v2 4축(status·owner·sev·queue) 비교로 실변경만 유지ticketSig()
채널단일 고정 — 이벤트 SLACK_CHANNEL_MAIN, 지연 요약 SLACK_CHANNEL_DELAYL712 / L901
유형별 제어타입 on/off만 — 유형→채널 매핑 불가notify_types_enabled
SLA 알림주기 요약만(off/1h/6h/24h) — 초과 시점 알림 없음notify-scheduler.ts
다이제스트시각 지정 불가. 24h는 “서버 기동 후 24시간마다”setInterval
결론: R4·R5·R6·R7은 현재 구조로 구현 불가. 채널이 env 상수에 박혀 있고 발송 시점이 스케줄러 주기에 종속된다.

2.2 SLA — 단일 시계의 한계

dueAt = createdAt + Sev별 목표일   (SEV1 1일 / SEV2 1일 / SEV3 3일 / SEV4 7일 / SEV5 미적용)
초과 판정 = KST 자정 기준 일(day) 단위
PENDING = 시계 정지 / PROJECT = endDateExpected 우회(코드 하드코딩)
보조 축 = 상태 체류(기본 전부 미사용)
한계구체적 문제
측정 축 1개생성→완료만 본다. “생성 후 3시간째 미배정”을 잡을 수 없다
시간 단위 부재overdueDays()가 일 단위 정수 → “2시간 내 배정” 표현 자체가 불가
차별화 축이 Sev뿐그룹·CTI·유형별 목표 차별화 불가 — CS 티켓과 구축 프로젝트가 같은 규칙
장기 건이 예외 처리PROJECT만 코드에서 제외하고 도메인 필드로 우회
초과 상태 미저장매 tick 전 티켓 재계산 → “초과된 그 순간” 1회 알림의 근거가 없다
달성 이력 없음준수/위반이 남지 않아 metric별 준수율 지표 불가

2.3 시스템 내부 알림 — 존재하지 않음

  • 개인 알림 테이블·벨·목록 없음. 유일한 선례는 위키 전용 wiki.wiki_notifications(댓글 알림)
  • notification_logs는 발송 감사 로그이지 알림함이 아니다 (수신자·읽음 개념 없음)
  • R2·R9를 만족할 자산이 0

2.4 첫 화면 — 전사 지표만

app/page.tsx(733줄): KPI 6타일 + 이번주·차주 구축 + 유지보수 7건 + 종별 도입 + 월별 추이. 개인 데이터가 한 줄도 없다. 개인화의 씨앗은 /tickets My Tickets 탭에만 있다.

4. SLA 모델 재설계 R10

4.1 3계층 구조

용어 (2026-07-26): 배정 그룹의 UI 표기는 Assignment Group(AWS SIM assigned/resolver group 대응). DB 테이블·컬럼(ticket_queues, queue_ids, queueId)과 API 경로는 유지 — 라벨만 변경.
계층테이블역할예
정책sla_policies어떤 티켓에 적용되나 + 시계 성격고객지원 그룹 · Sev1~2
타깃sla_targets무엇을 몇 분 안에배정 30분 / 해결 1일
시계ticket_sla_clocks티켓별 metric 실측 인스턴스TK-…-00042 ASSIGN 10:00→10:30 초과

티켓 1건이 여러 시계를 갖는다: ASSIGN + RESOLVE + UPDATE_STALE이 동시에 돌 수 있다.

4.2 metric 정의

metric시작(anchor)달성 조건용도
ASSIGN티켓 생성owner 최초 지정CS 미배정 방치 — “생성 3시간째 담당자 없음”
FIRST_RESPONSE티켓 생성첫 코멘트 또는 IN_PROGRESS 진입첫 응답 지연 (선택 도입)
RESOLVE티켓 생성RESOLVED/CLOSED현행 dueAt의 후계
UPDATE_STALE마지막 활동새 활동 시 리셋(재시작)장기 건 방치 — 프로젝트 3주간 기록 없음
DWELL특정 상태 진입그 상태 이탈상태별 체류(현 설정의 후계)
DOMAIN_DUE도메인 기한 필드RESOLVED/CLOSED기한을 도메인이 소유하는 경우

DOMAIN_DUE 앵커는 refType별 코드 고정 매핑: PROJECT=end_date_expected, SITE_VISIT=visit_date, INSTALL_PLAN=reply_date, 그 외 미지원(저장 시 400).

장기 프로젝트 문제의 답: 프로젝트 티켓은 RESOLVE를 걸지 않고 DOMAIN_DUE(완료예정일) + UPDATE_STALE(무응답) 조합을 쓴다. “6개월 걸리는 게 정상인 건”에 7일 SLA를 씌우는 현재의 왜곡이 사라진다.

4.3 정책 매칭·우선순위

매칭 축 (AND):  refTypes[] · queueIds[] · ctiIds[](서브트리 상속) · severities[] · isPure
빈 배열 = 해당 축 제한 없음(전체)
  • 여러 정책 매칭 시 priority 낮은 1개만 승리. 병합 없음 — 병합은 “어느 값이 이겼는지” 추적이 안 돼 운영 사고를 만든다
  • 승리 정책의 모든 활성 타깃이 시계로 인스턴스화
  • 타깃 severity가 NULL이면 전 Sev 공통, 값이 있으면 그 Sev에만
  • 매칭 결과를 시계에 policy_id/target_id로 박아 저장 → 정책을 바꿔도 진행 중 시계 기준은 불변(소급 재계산은 명시적 액션에서만)

4.4 시계 정지·재개

  • PENDING 정지(현행 관례 유지): 진입 시 paused_at, 이탈 시 paused_ms 누적 + due_at 뒤로 밀어 재계산. 정지 중 초과 판정 제외
  • 영업시간 시계(평일 09~18시만 카운트): 스키마 필드(clock_type)만 두고 1.1은 24시간 시계만 구현 — 공휴일 처리 없이는 반쪽이고 검증 비용이 크다 → 결정 D3

4.5 스키마 신규 3종

CREATE TABLE sla_policies (
  id SERIAL PRIMARY KEY, name VARCHAR(100) NOT NULL, description TEXT,
  priority INT NOT NULL DEFAULT 100,              -- 낮을수록 우선
  ref_types TEXT[] NOT NULL DEFAULT '{}',         -- 빈 배열 = 전체
  queue_ids INT[] NOT NULL DEFAULT '{}',
  cti_ids   INT[] NOT NULL DEFAULT '{}',          -- 서브트리 상속
  severities TEXT[] NOT NULL DEFAULT '{}',
  clock_type VARCHAR(20) NOT NULL DEFAULT 'CALENDAR_24H',
  is_active BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMP NOT NULL DEFAULT now(), updated_at TIMESTAMP NOT NULL DEFAULT now()
);

CREATE TABLE sla_targets (
  id SERIAL PRIMARY KEY,
  policy_id INT NOT NULL REFERENCES sla_policies(id) ON DELETE CASCADE,
  metric VARCHAR(20) NOT NULL,        -- ASSIGN|FIRST_RESPONSE|RESOLVE|UPDATE_STALE|DWELL|DOMAIN_DUE
  status_scope VARCHAR(20),           -- DWELL 전용
  severity VARCHAR(10),               -- NULL = 전 Sev
  threshold_min INT NOT NULL,         -- 목표(분). DOMAIN_DUE는 기한 대비 오프셋
  warn_ratio SMALLINT NOT NULL DEFAULT 80,  -- 목표의 N% 경과 시 임박(0=미사용)
  is_active BOOLEAN NOT NULL DEFAULT true,
  CONSTRAINT sla_targets_dwell_chk CHECK (metric <> 'DWELL' OR status_scope IS NOT NULL)
);

CREATE TABLE ticket_sla_clocks (
  id BIGSERIAL PRIMARY KEY,
  ticket_id INT NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  metric VARCHAR(20) NOT NULL, status_scope VARCHAR(20),
  policy_id INT REFERENCES sla_policies(id) ON DELETE SET NULL,
  target_id INT REFERENCES sla_targets(id) ON DELETE SET NULL,
  threshold_min INT NOT NULL,
  started_at TIMESTAMP NOT NULL, due_at TIMESTAMP NOT NULL,
  paused_at TIMESTAMP, paused_ms BIGINT NOT NULL DEFAULT 0,
  state VARCHAR(12) NOT NULL DEFAULT 'RUNNING',   -- RUNNING|PAUSED|MET|BREACHED|CANCELED
  satisfied_at TIMESTAMP, breached_at TIMESTAMP,
  notified_warn_at TIMESTAMP, notified_breach_at TIMESTAMP,  -- 1회성 보장 · quiet backfill 마킹
  created_at TIMESTAMP NOT NULL DEFAULT now(), updated_at TIMESTAMP NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ticket_sla_clocks_uniq ON ticket_sla_clocks (ticket_id, metric, COALESCE(status_scope,''));
-- 초과 스캔 전용 부분 인덱스 (tick 부하 억제)
CREATE INDEX ticket_sla_clocks_scan_idx ON ticket_sla_clocks (state, due_at)
  WHERE state = 'RUNNING' AND notified_breach_at IS NULL;

4.8 관리자 설정 화면 — SLA 지연 기준 편집 요구사항 핵심

요구: 티켓의 각 상태에서 지연 시 알림이 단계별로 시간 지정 가능해야 하고, 티켓 유형별로도 구분되어야 한다.

5.1 채널 라우팅 규칙 신규 2종

env 상수(SLACK_CHANNEL_MAIN/DELAY) 의존을 끊고 DB 규칙으로 전환한다.

CREATE TABLE notify_channels (
  id SERIAL PRIMARY KEY, name VARCHAR(60) NOT NULL,
  slack_channel_id VARCHAR(40) NOT NULL, description TEXT,
  is_active BOOLEAN NOT NULL DEFAULT true, sort_order INT NOT NULL DEFAULT 0
);

CREATE TABLE notify_routes (
  id SERIAL PRIMARY KEY, name VARCHAR(100) NOT NULL,
  event_type VARCHAR(30) NOT NULL,   -- TICKET_CREATED|TICKET_STATUS_CHANGED|TICKET_QUEUE_TRANSFERRED
                                     -- |SEV_ESCALATED|SLA_BREACH|SLA_WARNING|DAILY_DIGEST
  channel_id INT NOT NULL REFERENCES notify_channels(id) ON DELETE CASCADE,
  ref_types TEXT[] DEFAULT '{}', queue_ids INT[] DEFAULT '{}', cti_ids INT[] DEFAULT '{}',
  severities TEXT[] DEFAULT '{}',
  status_to TEXT[] DEFAULT '{}',     -- "이 상태로 바뀔 때만"
  metrics TEXT[] DEFAULT '{}',       -- SLA 이벤트에서 대상 metric 한정
  mention_mode VARCHAR(20) NOT NULL DEFAULT 'none',  -- none|queue_members|channel|here
  digest_hour SMALLINT,              -- DAILY_DIGEST 전용 (KST 0~23)
  digest_opts JSONB,                 -- { kinds, groupBy, maxPerSection }
  is_active BOOLEAN NOT NULL DEFAULT true, sort_order INT NOT NULL DEFAULT 0
);
매칭 의미론 — SLA 정책과 동일 규칙을 쓴다(두 곳에서 다르면 운영자가 혼동한다).
  • 축 간 AND, 배열 내부 OR, 빈 배열 = 제한 없음, cti_ids는 서브트리 상속
  • 정책과 다른 점: 라우팅은 매칭된 규칙 전부 실행(다중 채널이 R7의 요구). 단 같은 채널 중복 매칭은 1건만 발송
  • 규칙 0건 매칭 = 미발송 + skipped/no_route 로그 (조용한 실패 아님)

기존 동작 보존용 시드 규칙 3행

규칙event_type채널스코프
전체 티켓 등록TICKET_CREATED현 MAIN전체

5.2 SLA 초과 즉시 알림 R4

tick(기본 5분)
 1) SELECT … FROM ticket_sla_clocks
    WHERE state='RUNNING' AND notified_breach_at IS NULL AND due_at <= now()
    ORDER BY due_at LIMIT :tickCap          ← 부분 인덱스 사용
 2) state='BREACHED', breached_at=now() 마킹
 3) notify-center emit(kind='SLA_BREACH')   ← 내부 알림(owner·참여자)
 4) notify_routes(SLA_BREACH) 매칭 채널로 개별 발송
 5) notified_breach_at=now()                ← 1회성 보장
폭주 방지 3중 장치 — 없으면 기능을 켜는 순간 수백 건이 쏟아진다.
  1. quiet backfill: 도입 시 이미 기한 지난 시계는 알림 없이 BREACHED 마킹 → 이후 새로 초과되는 건만 알림
  2. tick 캡(기본 20): 초과분이 캡을 넘으면 다음 tick으로, 미발송분은 다이제스트가 커버
  3. metric 한정: 규칙의 metrics[]로 “즉시 알림은 ASSIGN·Sev1 RESOLVE만” 축소 가능(D5)

임박 알림(SLA_WARNING)도 같은 흐름 — warn_ratio 경과 시 notified_warn_at 1회.

5.3 일 1회 다이제스트 R5

  • 규칙별 digest_hour(KST) 보유. tick마다 판정: “지금 KST 시각 ≥ digest_hour” AND “오늘 이 규칙 발송 로그 없음” → 발송
  • 발송 여부 근거는 notification_logs(payload.routeId + KST 당일) → 서버 재시작에도 중복되지 않는다(현행 setInterval의 약점 해소)
  • 내용: 초과 전체 리스트(+임박·체류 선택), groupBy(큐/유형) 섹션, 섹션당 최대 20건(현행 10 → 상향), metric 표기(“ASSIGN 3시간 초과”, “완료예정일 5일 경과”)
  • 현행 12시간 dedup은 삭제 — 하루 1회 규칙이 그 역할을 대체

5.4 유형별 생성·상태변경 알림 R6 R7

  • 발송 판단은 기존 sig v2 4축 비교 그대로 유지(이중발송 0건은 P11에서 검증된 자산)
  • 달라지는 건 “어디로 보내나”뿐: 단일 MAIN → 매칭된 N개 채널
  • status_to[]로 “완료로 바뀔 때만 공지 채널”, severities[]로 “Sev1~2만 임원 채널”
  • 기존 타입·이벤트 토글은 전역 킬스위치로 존치 — 규칙이 늘어도 “일단 다 끄기”가 가능해야 한다

  • 티켓 상세에 SLA 시계 패널: metric별 기한·잔여/초과·정지 이력. 담당자가 “무엇 때문에 위반인지” 알 수 있어야 한다

8. 지표 반영 (기존 P12 대시보드 확장)

  • metric별 SLA 준수율(ASSIGN / RESOLVE / DOMAIN_DUE) 추이 — 현행 단일 준수율 대체
  • 평균 배정 소요시간(ASSIGN 실측) — CS 응답성의 핵심 지표
  • 초과 발생 Top 그룹·유형, metric별 위반 건수
  • 소스는 ticket_sla_clocks(달성·초과가 행에 남아 raw SQL 집계 가능)

9. Phase 계획·게이트

순서 원칙(2026-07-26 사용자 요구 반영): 관리자가 설정에서 기준을 만질 수 있는 상태가 알림 발송보다 먼저여야 한다. SLA 설정 UI를 P6 → P2로 앞당기고 발송을 뒤로 미뤘다. P1~P3은 알림 동작이 전혀 바뀌지 않는 구간이라 운영 리스크 없이 선행 가능.
P0
설계 확정 — 결정 항목
게이트: 사용자 승인 → 2026-07-26 완료
P1
SLA 엔진 — 스키마 3종 + lib/sla.ts(매칭·생성·정지·판정) + 티켓 mutation 훅 + 폴백 정책 시드(기존 값 이관) + quiet backfill
게이트: 시계 단위 테스트(정지·재개·달성·초과·UPDATE_STALE 리셋) / 기존 dueAt 동등성 / 백필 후 알림 0건 / tsc 0오류
P2
SLA 설정 화면(탭①) — 상태 지연 매트릭스 + 처리 목표 매트릭스 + 정책 행 추가·정렬 + 적용 범위 선택 + 영향 미리보기 + 정책·타깃 CRUD API
게이트: 유형×상태 셀 편집 → 신규 티켓 시계 반영 / “열린 티켓에 지금 적용” 재계산 후 알림 0건 / 미리보기 숫자 = 실제 매칭 / 우선순위 드래그 / ADMIN 이상만
P3
채널·라우팅(탭②③) — 스키마 2종 + lib/notify-routes.ts + 채널 결정 전환 + 규칙 CRUD·미리보기
게이트: 시드 규칙만으로 1.0과 동일 발송(회귀) / 다중 채널·같은 채널 dedup / 규칙 0건=미발송+로그 / test 모드 강등 유지
P4
즉시 초과 알림 + 다이제스트 — tick 재설계 + breach 스캔 + 지정 시각 발송
게이트: 초과 → 5분 내 1건, 재발송 0 / tick 캡 / 재시작 후에도 하루 1회 / KST 정확 / 설정 변경이 다음 tick부터 반영
P5
내부 알림(탭④) — 스키마 2종 + notify-center.ts + 벨 + /notifications + 개인 설정
게이트: Slack off에서도 적재 / 본인 행동 제외 / dedup / 읽음 처리 / 위키 알림 합산 / 모바일
P6
첫 화면 개인화 — /api/me/dashboard + My Work + 목록 SLA 필터 + 상세 SLA 시계 패널
게이트: 1콜 <300ms / 권한별 렌더 / 초과 클릭 → 해당 티켓 / 모바일 카드
P7
지표 확장 + 문서 + PROD 배포
게이트: 지표 수기 대조 / 배포 절차서(마이그레이션 7종·시드·quiet backfill 순서) / 스모크

10. 마이그레이션·리스크·롤백

10.1 마이그레이션

신규 테이블 7종(sla_policies, sla_targets, ticket_sla_clocks, notify_channels, notify_routes, notifications, notification_prefs) — 모두 순수 추가, 기존 테이블 변경 없음.

마이그레이션 → prisma generate → 시드(정책·타깃·채널·규칙 3행)
→ quiet backfill(시계 생성 + 초과분 알림 없이 마킹) → 빌드 → PM2 재시작 → 스모크
PROD DB 작업은 사용자 명시 허락 후(절대규칙 #5).

10.2 리스크

리스크영향대응
초과 알림 폭주도입 순간 수백 건quiet backfill + tick 캡 + metric 한정
채널 오발송잘못된 채널에 업무 정보 노출test 모드 유지 + 채널 등록 시 연결 테스트 필수 + 규칙 미리보기
시계 오계산오탐 → 알림 신뢰도 붕괴P1을 알림 없이 먼저 안정화 + dueAt 동등성 대조. 오탐 1건이 기능 전체를 불신하게 만든다
tick 부하(5분)DB 부하부분 인덱스 + LIMIT 스캔(전 티켓 재계산인 현행보다 가벼움)
내부 알림 스팸벨 무시 → R2 무의미보수적 기본값 + 개인 설정 + 본인 행동 제외
규칙 폭발운영자가 이해 못 함미리보기·정렬·활성 토글 + “정책은 1개 승리, 라우팅은 전부 실행” UI 명시
이중 발송같은 이벤트 여러 규칙채널 단위 dedup + sig v2 유지 (P2 게이트)

10.3 롤백

  • 알림만 되돌리기: notify_routes 전 행 비활성 또는 notify_enabled=off → 즉시 무발송
  • 코드 롤백: 이전 커밋 pull + 빌드. 신규 테이블은 남겨도 무해(순수 추가)
  • 시계가 잘못되면 ticket_sla_clocks 전체 삭제 후 재백필 가능(원본이 아닌 파생 데이터)

CLAUDE.md 설계 게이트 원칙 — 결정 없이 임의 진행하지 않는다. ★ = 권장안

12. 범위 외 — 페이저 앱으로 가는 길

이번 설계가 페이저 앱(R3)의 필요 조건 3개를 미리 만든다.
  1. 사용자별 알림 레코드(notifications) — 푸시할 대상이 DB에 있어야 앱이 붙는다
  2. kind·severity 체계 — 페이저는 “깨울 것/안 깨울 것”을 구분해야 하고, 그 판단 축이 kind + severity + SLA metric이다
  3. 개인 수신 설정(notification_prefs) — 채널만 늘리면(push 컬럼 추가) 그대로 확장된다
향후 추가로 필요한 것(이번 범위 아님): 디바이스 토큰 테이블, 푸시 게이트웨이(FCM/APNs·웹푸시), 미확인 시 에스컬레이션 체인, 당직(on-call) 스케줄. 온콜은 그룹 멤버십(ticket_queue_members)의 자연스러운 확장이 될 것이다.
