## 3. 아키텍처 결정

### 3.1 별도 모바일 셸 `/m/*` (반응형 페이지를 그대로 설치하지 않는 이유)
- 데스크톱 화면은 반응형이지만 정보량이 많고 메뉴 깊이가 깊다. 현장에서는 "주차 등록", "스캔해서 출고"처럼 **한 손·몇 탭**으로 끝나야 한다
- `/m/*`는 전용 레이아웃(상단 제목줄 + 하단 탭 4개)을 쓰고 데스크톱 `Navigation`을 숨긴다. 데이터는 전부 기존 API를 호출한다(차량 모바일 페이지 선례와 동일)
- 데스크톱 상세가 필요하면 링크로 연다(앱 범위 밖이라 브라우저 바가 붙어 뒤로가기·닫기가 보장됨)

### 3.2 같은 레포·같은 Next 앱
- 배포·인증·타입·API 계약을 공유한다. 빌드 산출물도 하나라 PROD 반영 절차(CLAUDE.md 규칙 6)가 그대로 적용된다
- 위키 경계 규칙(규칙 7)과 무관하다. `/m/*`는 메인 모듈이다

### 3.3 앱 범위(scope)는 `/m/` — 슬래시 포함이 필수
- manifest `scope`와 SW scope는 **문자열 접두 일치**다. `/m`으로 두면 `/maintenances`까지 앱 범위가 된다 → 반드시 **`/m/`**
- 그래서 홈은 `/m/home`, `start_url`도 `/m/home`. `/m`으로 들어오면 `/m/home`으로 리다이렉트
- **로그인도 범위 안(`/m/login`)에 둔다.** iOS 홈 화면 앱에서 범위 밖 `/login`으로 나가면 별도 브라우저 뷰가 열려 쿠키가 앱과 공유되지 않는 경우가 있다. 데스크톱 `/login`은 손대지 않는다
- 미들웨어: 비로그인 상태로 `/m/*` 접근 시 `/login` 대신 **`/m/login?next=<원래 경로>`** 로 보낸다. `next`는 `/m/`로 시작하는 값만 허용(오픈 리다이렉트 방지)

### 3.4 서비스 워커는 최소한으로
- 파일 `public/m-sw.js`, scope `/m/`. 기존 사이니지 `sw.js`(scope `/dashboard`)와 겹치지 않는다
- 하는 일은 **문서 요청이 네트워크 실패·5xx일 때 오프라인 안내 페이지(`/m-offline.html`)를 보여주는 것뿐**. 사이니지 SW와 같은 패턴이다
- API·데이터는 캐시하지 않는다. 재고·주차는 실시간 값이어야 하고, 오래된 재고를 보고 출고하는 사고가 캐시의 이득보다 크다
- 설치 가능성 요건(manifest + HTTPS + SW)을 충족하는 목적도 겸한다

### 3.5 바코드 스캔 엔진
- 브라우저 표준 `BarcodeDetector`는 **Android Chrome만 지원하고 iOS Safari는 미지원**이다
- → npm **`barcode-detector`**(zxing-cpp WASM 기반 폴리필) 채택: 네이티브가 있으면 네이티브, 없으면 WASM으로 같은 API를 쓴다. DataMatrix·QR·Code128·Code39·EAN 지원
- WASM 파일은 기본값이 외부 CDN 로드다 → **`public/vendor/`에 버전명을 붙여 커밋하고 그 경로를 지정**(사내 도구가 외부 CDN 가용성에 묶이지 않게). 정확한 버전·import 경로는 구현 시점에 확인
- 카메라는 HTTPS에서만 열린다. `dev.ops.seersthync.com`·PROD는 HTTPS라 문제없음. **dev2(WSL 로컬)는 폰에서 HTTPS 접근이 안 되므로 현장 테스트는 이 호스트의 dev 도메인에서**

## 4. M0 — PWA 기반 + 로그인

### 4.1 설치
- `app/manifest.ts` — `name`/`short_name` "thynC Ops", `start_url` `/m/home`, `scope` `/m/`, `display` `standalone`, 테마색은 기존 `themeColor`와 동일, 아이콘 192·512·maskable 512
- `public/icons/` — `logo.svg`로 192·512·maskable·apple-touch-icon(180) PNG 생성
- 루트 `metadata.appleWebApp`에 `capable: true`, `statusBarStyle` 추가(데스크톱 영향 없음)
- 설치 안내: `/m/home`에서 standalone이 아니면 접이식 배너. Android는 설치 버튼(`beforeinstallprompt`), iOS는 "공유 → 홈 화면에 추가" 그림 안내. 닫으면 localStorage로 숨김

### 4.2 모바일 셸
- `app/m/layout.tsx` — 상단 제목줄(뒤로·제목·사용자 이니셜) + **하단 탭 [홈][주차][자재][조회]** + safe-area 패딩 + SW 등록
- `Navigation.tsx`·`MainWrapper.tsx`의 전체화면 판정에 `pathname === '/m' || pathname.startsWith('/m/')` 추가 (`startsWith('/m')`는 `/maintenances`와 충돌하므로 금지)
- `/m/home` — 인사 + 큰 타일 3개(주차 등록 · 자재 입출고 · 시리얼 조회) + "PC 화면 열기" 링크 + 로그아웃. 권한 없는 타일은 숨기지 않고 읽기 전용 표시(§6.7)

### 4.3 로그인 `/m/login`
- 기존 `POST /api/auth/login`을 그대로 호출. 이메일 정규화·감사 로그·비활성 계정 차단 모두 기존 로직
- 성공 시 `next`(검증된 `/m/` 경로) 또는 `/m/home`으로 이동, `router.refresh()`
- 미들웨어 공개 경로 추가: `/m/login`, `/manifest.webmanifest`, `/m-sw.js`, `/m-offline.html`, `/icons/*`, `/vendor/*`
- 세션 수명은 **결정 D-1**

### 4.4 데스크톱에서 진입
- 데스크톱 모바일 드로어(폰으로 PC 화면을 연 경우) 하단에 "모바일 앱으로 열기 → /m/home" 링크 (결정 D-4). UA 기반 자동 리다이렉트는 하지 않는다 — 폰에서 PC 화면을 쓰는 사용자도 있다

## 5. M1 — 주차 등록 `/m/parking`

서버 변경 없음. 데스크톱 `/parking`의 흐름을 현장용으로 줄인다.

1. **차량 검색** — 숫자 키패드(`inputMode="numeric"`)로 뒤 4자리 입력, 입차일 칩 **[오늘][어제][날짜]**(전날 입차건 실패 사례 2026-10-07 반영 — 검색에 쓴 입차일을 이후 모든 호출에 전달). 최근 검색 차량 5개를 칩으로 제공(localStorage, 기기 로컬 편의 기능)
2. **차량 선택** — 결과 카드(차량번호·입차시각·경과·기등록 할인 건수). 1건이면 자동 선택
3. **자동 계산 미리보기** — `POST /api/parking/plan` 결과를 큰 글씨로: 주차 시간 · 커버 목표 · 추가할 할인권(무료/유료 묶음) · 예상 비용 · 재입차 무료권 차단 안내
4. **[자동 등록]** — 화면 하단 고정 버튼. 확인 바텀시트 후 `POST /api/parking/auto-apply`. 결과를 단계별 ✓/✗로 표시, 실패 시 서버 메시지 그대로
5. **수동 등록**(접이식) — `POST /api/parking/coupons`로 계정별 할인권 목록 → 항목 탭 → `POST /api/parking/register`
- VIEWER는 검색·미리보기만 가능(등록 API가 403). 버튼 대신 안내 문구

## 6. M2 — 자재 입출고 + 카메라 스캔

### 6.1 스캔 컴포넌트 `BarcodeScanner`
- 바텀시트 전체화면 카메라(후면, 1280×720 이상 요청), 가운데 조준 영역, **연속 스캔 모드**: 시트를 닫지 않고 계속 읽는다
- 인식 시 피드백: 초록/빨강 테두리 플래시 + 짧은 비프(WebAudio) + 진동(`navigator.vibrate` — Android만, iOS는 무시됨) + 상단 카운터 "12개"
- 중복 억제: 같은 값은 1.5초 쿨다운, 이미 담긴 시리얼은 "이미 추가됨"으로 무시
- 손전등 토글(지원 기기만 — 주로 Android), 카메라 권한 거부 시 설정 안내
- **수동 입력란 상시 제공** — 라벨 손상 대비 + 블루투스/USB 바코드 리더(키보드 입력)도 같은 입력란으로 연속 스캔 가능
- 디코딩 루프 초당 약 8~10회. WASM 디코드는 메인 스레드로 시작하고 버벅이면 Worker로 이전(구현 판단)

### 6.2 스캔 파서 `lib/scanParse.ts` (클라이언트·서버 공용 순수 함수)
입력 = 디코더 원문(raw), 출력 = `{ serialCandidates[], lot?, gtin?, expiry?, kind, raw }`

| 순서 | 판정 | 처리 |
|---|---|---|
| 1 | 심볼 식별자 접두 `]d2`·`]Q3`·`]C1` | 제거 |
| 2 | **GS1 원소열** — GS(`\x1D`) 구분자 포함 또는 `01`+14자리로 시작 | AI 파싱: `01` GTIN(14) · `11`/`17` 날짜(6) · `10` LOT(가변) · `21` 시리얼(가변, GS 또는 끝에서 종료) |
| 3 | **괄호 표기** `(01)…(17)…(10)…(21)…` | 같은 AI 규칙으로 파싱 |
| 4 | 게이트웨이 합성형 `GW####-B######` | **원문 그대로가 1순위**(WMS 저장 형식), 접미 `B######`을 2순위 후보 |
| 5 | 기기 바코드형 `XXX0000-A000000` | 접미 시리얼(`A000000`) 1순위, 원문 2순위 (`lib/deviceRegistryShared.ts` `normalizeSerial` 규칙과 동일) |
| 6 | 그 외 | 공백 제거·대문자화한 값 하나 |

- GTIN은 기존 `isValidGtin`으로 체크디지트 검증
- **검증 스크립트** `scripts/verify-scan-parse.mts`(DB 불필요 픽스처, `verify-hospital-matcher.mts` 선례) — M2-0에서 수집한 실제 라벨 원문을 픽스처로 고정

> ⚠️ **실제 라벨 형식은 아직 모른다.** 심전계·산소포화도에 GS1 DataMatrix(UDI)가 붙어 있는지, 시리얼만 Code128로 찍혀 있는지, 게이트웨이 박스·본체 라벨이 합성형인지 확인이 필요하다. 그래서 **M2-0 라벨 실측을 게이트로 둔다**(§8).

### 6.3 신규 API `GET /api/inventory/units/lookup?code=<raw>` (읽기 전용)
- 왜 필요한가: 출고·이동 API는 `itemId`·`warehouseId`를 먼저 받아야 한다. "스캔 먼저" 흐름은 시리얼만 보고 **그 개체가 어느 품목·위치에 있는지** 알아야 하는데, 기존 `GET /api/inventory/units`에는 시리얼 검색이 없다
- 처리: 서버에서 `scanParse` → 후보 시리얼로 `inventory_units` 조회(`serial_no IN 후보`) → 개체마다 품목(id·코드·이름·모델·LOT 관리 여부·`udiDi`)·인벤토리·위치·상태·LOT·출고 병원 반환. GTIN이 있으면 `udi_di` 일치 품목 목록도 반환
- 같은 시리얼이 여러 품목에 있을 수 있다(326건) → 배열로 반환하고 화면이 상태로 좁힌다
- 권한: 로그인 사용자 전원(기존 `GET /api/inventory/units`와 동일 수준). 쓰기 없음
- 인덱스: 시리얼 단독 조회는 기존 `(item_id, serial_no)` 인덱스를 못 탄다. 2만 행이라 v1은 순차 스캔으로 충분, 느려지면 `serial_no` 인덱스 추가(그때 마이그레이션)

### 6.4 출고 흐름 (스캔 먼저)
1. [출고] 선택 → 바로 스캐너 오픈
2. **첫 스캔**이 전표 문맥을 정한다 — 조회 결과 중 `IN_STOCK` 개체가 정확히 1건이면 그 품목·인벤토리·위치로 고정. 2건 이상이면 고르게 하고, 0건이면 사유 표시("미등록 시리얼", "이미 출고됨 — ○○병원" 등)
3. **이후 스캔**은 같은 품목·같은 위치·`IN_STOCK`만 담는다. 다른 품목은 "다른 품목입니다 — 이 전표를 먼저 처리하세요"로 거절(v1 = 1전표 1품목, 결정 D-3)
4. 스캐너를 닫으면 확인 화면: 품목·위치·수량·시리얼 목록(스와이프 삭제) + 입력값
   - 출고 유형(필수): 마스터 `STOCK_OUT_TYPE`(영업·판매·폐기·불량·기타)
   - 요청자(필수): 기본값 = 로그인 사용자 이름
   - 출고처(선택) · 병원(선택, 검색) · 입출고일(기본 오늘) · 비고
5. [출고 처리] → 기존 `POST /api/inventory/transactions` `{ txType:'OUT', itemId, warehouseId, quantity, serials, … }`. 서버가 개체 상태·위치를 다시 검증하고 동시성 가드로 이중 출고를 막는다. 409면 서버 메시지 그대로 보여주고 목록 유지
6. 성공 → 전표코드 `STK-…` + "PC에서 전표 보기" 링크, `router.refresh()`

### 6.5 이동 흐름
- 출고와 같은 "스캔 먼저". 확인 화면에서 **도착 위치**(같은 인벤토리 위치 목록) 선택 → `txType:'MOVE'` + `toWarehouseId`

### 6.6 입고 흐름 (품목 먼저)
신규 시리얼은 아직 DB에 없어 스캔만으로 품목을 알 수 없다.
1. 입고 유형 선택: 구매 · 회수(반품) · 기타
2. 품목·위치 선택 — 인벤토리 → 품목 검색 → 위치. **GS1 라벨을 먼저 스캔하면 GTIN으로 품목 후보를 좁혀 준다**(같은 GTIN이 인벤토리별로 3품목 → 인벤토리 선택은 사람)
3. 연속 스캔 — 판정:
   - 구매·기타: 같은 품목에 이미 있는 시리얼이면 거절("이미 등록된 시리얼")
   - 회수: 같은 품목에 `OUT` 상태 개체가 있어야 정상. 없으면 "미등록(도입 전 출고분)" 표시 후 담기 허용 → 제출 시 서버 409 `UNKNOWN_RETURN_SERIALS` → 확인 바텀시트 → `allowUnknownReturn:true` 재전송(데스크톱과 동일 계약)
   - 스캔한 GTIN이 선택 품목 `udiDi`와 다르면 경고(담기는 허용 — UDI는 품목 속성이라 오입고 신호)
4. **LOT** — LOT 관리 품목은 시리얼별 LOT 필수. GS1 라벨의 AI `10`이 있으면 시리얼마다 자동 채움. 없으면 "공통 LOT" 입력란 값을 일괄 적용. 비어 있으면 제출 전 차단
5. 제출 → `POST /api/inventory/transactions` `{ txType:'IN', reasonId, itemId, warehouseId, quantity, serials, lotBySerial }`

### 6.7 권한 · 노출
- 입출고 처리: 기존 `GET /api/inventory/can-manage`의 `canManage`(ADMIN 이상 · 재고 담당자 풀 · RBAC `inventory.manage`/`inventory.admin`). 서버도 기존대로 `canManageStock`으로 재검사
- 권한이 없으면 [자재] 탭은 **조회 전용**(시리얼 조회 + 품목 현재고). 새 권한 키는 만들지 않는다(RBAC 규칙 1)

### 6.8 v1에서 다루지 않는 것 (안내 문구로 처리)
- **비시리얼 품목**: 품목 선택 + 수량 스테퍼로 단순 입출고만 지원. 비시리얼 **LOT** 품목은 "PC에서 처리" 안내(LOT 버킷 선택 UI가 복잡)
- **세트출고 부자재**: 부자재 매핑이 있는 품목을 출고하면 "부자재 동시 출고는 PC에서" 안내 (결정 D-2)
- **프로젝트 출고**: 프로젝트에 연결된 기기 출고는 **출고업무(출고요청) 처리**가 정식 경로다 — 그 경로만 기기현황 자동 등록·티켓 종결이 함께 된다. 모바일 v1 출고는 데스크톱 자재 현황 모달과 같은 일반 WMS 전표이며, 화면에 이 차이를 한 줄 안내. 출고요청 처리 스캔은 v1.1 1순위 후보

## 10. 리스크 · 알려진 제약

- **토큰 즉시 폐기 불가 (기존 구조)**: JWT를 DB와 대조하지 않아, 계정을 비활성화해도 이미 발급된 토큰은 만료까지 유효하다(미들웨어는 토큰 안의 `isActive`만 본다). 폰 분실 시 노출 기간 = 세션 수명이라 D-1과 직결된다. 근본 해결(토큰 버전 컬럼 또는 DB 재확인)은 전 시스템 영향이라 **별도 과제로 제안**하고 v1에는 넣지 않는다
- **iOS 카메라 권한 재요청**: iOS 홈 화면 앱은 실행할 때마다 카메라 권한을 다시 물을 수 있다(플랫폼 동작). 안내 문구로 대응
- **작은 DataMatrix 초점**: 일부 Android 기기는 근접 초점이 약하다. 손전등·확대 안내, 실패 시 수동 입력
- **iOS 저장 공간 정리**: iOS는 오래 안 쓴 PWA의 저장소를 지울 수 있다. v1은 localStorage에 편의 정보(최근 차량·배너 숨김)만 두므로 영향 미미
- **dev2 현장 테스트 불가**: 카메라는 HTTPS 필수 → 폰 테스트는 이 호스트 dev 도메인에서(빌드·재시작은 사용자 요청 시)

## 12-1. 메뉴 재구성 (2026-11-04 프로토타입 리뷰)

- 사용자 리뷰 결과 홈 메뉴를 **주차등록 · 출고요청 · 자재관리** 3개로 재구성. 하단 탭도 [홈][주차등록][출고요청][자재관리]

- 주차등록은 프로토타입 그대로 유지
