# 사용량 — 전체 병원 화면 (서비스 단위 가동률) 설계안

> **상태: 완료 — PROD 반영 2026-11-21 (48a6766)**. 제안값(§2)으로 구현했고 사용자가 화면을 보고 "보기 좋다, 유지"(2026-11-20). 판정 기준값(±5%p · 14일)은 병원이 늘어난 뒤 다시 본다 (구현 노트 §9)
> 관련: [usage_collection_design.md](usage_collection_design.md) §14 (병원별 화면 `/usage` — 지표 정의의 단일 소스는 `lib/usage/metrics.ts`·`daily.ts`)

---

## 1. 이 화면이 답하는 질문

병원별 화면은 병원 한 곳을 깊이 본다. 이 화면은 수집 중인 전체 병원을 한 표에 놓고 **어느 병원을 들여다봐야 하는지**를 골라낸다.

1. 가동률이 높은 병원, 낮은 병원은 어디인가 (상위 · 하위 10곳)
2. 가동률이 오르고 있는 병원, 떨어지고 있는 병원은 어디인가
3. 서비스 전체로는 도입 기기의 몇 %가 돌고 있는가

여기서 걸러낸 병원을 누르면 기존 병원별 화면으로 넘어가고, 상세 분석은 사람이 그 화면에서 한다. 이 화면은 원인을 설명하지 않는다.

## 2. 검토가 필요한 결정 (제안값)

| # | 항목 | 제안 | 이유 |
|---|---|---|---|
| D1 | 순위의 기준 가동률 | **동시 가동률**(그날 최대 동시사용 수 ÷ 그날의 계약·공급 수량). 기기는 골라 본다 — 심전계(기본) · 산소포화도 · 카트온 | 일자별 표의 `31 / 150 (21%)`와 같은 값. 기기 종류마다 수량이 달라 하나로 합치면 뜻이 흐려진다 |
| D2 | 비교 기간 | **최근 30일 평균 vs 그 전 30일 평균**. 최근 30일은 병원별 화면의 '30일'과 같은 날짜 범위(평균에서 오늘 제외) | 표의 숫자와 눌러 들어간 병원별 화면의 '동시 가동률 평균'이 같은 값이 된다 |
| D3 | 증가 · 감소 판정 | 변화 = 최근 평균 − 이전 평균(%p). **+5%p 이상 = 증가, −5%p 이하 = 감소**. 두 기간 중 하나라도 유효한 날이 14일 미만이면 '판정 보류' | 상대 변화(%)는 가동률이 낮은 병원에서 과하게 튄다(2% → 4%가 +100%). 기준값은 병원이 늘어난 뒤 실데이터를 보고 조정 |
| D4 | 화면 형태 | 상위 · 하위 · 증가 · 감소를 따로 나열하지 않고 **병원 표 하나 + 빠른 필터** | 같은 병원이 여러 목록에 겹쳐 나오지 않고, 2곳일 때도 100곳일 때도 같은 모양 |
| D5 | 진입 | 메뉴 '사용량'의 첫 화면을 전체 병원 화면으로. 병원을 누르면 기존 병원별 화면(`/usage?hospital=코드`) | 병원 상세의 '사용량 보기' 링크 등 기존 주소는 그대로 동작 |
| D6 | 판매모델 | 병원별 화면과 같은 선택(합산 · 일반형 · 사용량비례형)을 둔다 | 사용량비례형은 사용량이 곧 매출이라 따로 볼 이유가 있다. 눌러 들어갈 때 선택이 이어진다 |
| D7 | 계산 방식 | **일별 집계를 본체 DB에 저장**하고 1시간마다 갱신. 화면은 집계만 읽는다 | 지금은 병원 한 곳을 원본에서 계산하는 데 약 2초. 전 병원을 열 때마다 계산할 수 없다 (§5) |
| D8 | 모듈 경계 예외 | `instrumentation.ts` → `lib/usage`의 집계 스케줄러 기동 1건 허용 | 위키 청크 스케줄러와 같은 형태. 그 밖의 메인 모듈은 지금처럼 `/api/usage/*`만 호출 (§5.4) |

## 3. 정의

지표 자체는 새로 만들지 않는다. 병원별 화면의 일별 값(최대 동시사용 수, 계약·공급 수량)을 그대로 쓰고, 기간으로 묶는 규칙만 더한다. 구현은 `lib/usage/overview.ts`(순수 함수)에 두고 '산정기준' 팝업에 절을 추가한다.

| 값 | 정의 |
|---|---|
| 유효한 날 | 그 기기의 계약·공급 수량이 있고, 기기별 수치가 있고(보관 기한 경과로 비는 날 제외), 오늘이 아니며, 그 병원의 마지막 수신 시각 이전인 날 |
| 가동률 (최근 30일) | 유효한 날의 일별 동시 가동률 평균 — 병원별 화면 '동시 가동률 평균'과 같은 계산 |
| 평균 최대 동시 / 수량 | 유효한 날의 최대 동시사용 수 평균 / 오늘 기준 계약·공급 수량. 표에는 `31 / 150 (21%)` 형태로, 비율을 굵게 |
| 이전 30일 | 최근 30일 바로 앞 30일의 같은 평균 |
| 변화 | 최근 − 이전 (%p) |
| 판정 | 증가(+5%p 이상) · 감소(−5%p 이하) · 유지 · 판정 보류(어느 한 기간의 유효한 날이 14일 미만) |
| 12주 추이 | 주(월~일)별 동시 가동률 평균 12개 — 병원별 화면 주간 통계의 값 |
| 전체 가동률 | Σ(병원별 평균 최대 동시) ÷ Σ(병원별 수량). 수량이 큰 병원이 더 많이 반영된다 (병원 가동률의 단순 평균이 아니다) |

**잘못 읽기 쉬운 경우는 표에 표시한다.**

- **수량 변동**: 두 기간 사이에 계약·공급 수량이 바뀐 병원(추가 도입 등). 사용이 그대로여도 분모가 커져 가동률이 떨어진다. 변화 옆에 '수량 150 → 300' 표시.
- **수신 지연**: 마지막 수신이 24시간을 넘긴 병원. Agent가 멈추면 새 측정이 들어오지 않아 가동률이 떨어지는 것처럼 보이므로, 마지막 수신 이후의 날은 평균에서 빼고 배지를 붙인다.
- **수량 없음**: 수집은 되는데 그 기기의 계약·공급 수량이 없는 병원. 가동률 '—'로 표 아래쪽에 남긴다(숨기지 않는다 — 딜 입력이 빠진 병원을 찾는 단서).
- **이력 따라잡는 중**: Agent가 기기 상태 이력을 아직 다 보내지 못한 병원은 과거 가동률이 낮게 나온다(2026-11-18 화순성심 사례). 판정 보류로 둔다.

## 4. 화면 구성

```
사용량 — 전체 병원                          집계 11-19 13:05 · 수집 병원 2곳   [산정기준]
기기 [심전계] [산소포화도] [카트온]      판매모델 [합산] [일반형] [사용량비례형]

전체 가동률 26% (44 / 170대) · 이전 30일 대비 +1%p   │   증가 0곳 · 감소 0곳 · 판정 보류 0곳

[전체 2] [상위 10] [하위 10] [증가 0] [감소 0] [판정 보류 0]                 병원 검색 [        ]

 #   병원            가동률 (최근 30일)             이전 30일   변화       12주 추이      수신
 1   동수원병원      13 / 20 (65%)  ████████▌      61%         ▲ +4%p    ▂▃▅▆▆▇▆▇▇▆▇▇    정상
 2   화순성심병원    31 / 150 (21%) ██▋            20%         ▲ +1%p    ▃▃▄▄▅▅▄▅▅▄▅▅    정상
```

(숫자는 모양을 보이기 위한 예시다.)

- **표 하나**가 본문이다. 기본 정렬은 가동률 높은 순. 열 머리글(가동률 · 이전 30일 · 변화)을 누르면 그 열로 정렬한다 — '변화' 내림차순이 곧 "늘고 있는 병원" 목록이다.
- **빠른 필터**: 상위 10 · 하위 10은 가동률 순위로, 증가 · 감소 · 판정 보류는 D3 판정으로 거른다. 괄호 안은 해당 병원 수.
- **행을 누르면** `/usage?hospital=코드&days=30&model=선택값`으로 이동한다. 병원별 화면에는 '← 전체 병원' 링크를 더한다.
- **요약은 한 줄**만 둔다. 서비스 전체 추이 그래프는 넣지 않는다(§7).
- 병원이 2곳인 지금은 상위 · 하위 필터가 의미 없지만 화면 구조는 그대로다. 병원이 없으면 같은 표에 '아직 수집 중인 병원이 없습니다'.
- 볼 수 있는 사람은 병원별 화면과 같다(`lib/usage/access.ts` — USER 이상 또는 `usage.view`, SEERS 소속. 2026-11-24 ADMIN 이상에서 넓힘).

## 5. 계산 구조

### 5.1 왜 미리 집계하는가

- 병원별 화면은 열 때마다 원본에서 계산한다. 주간 통계(약 90일) 기준 병원 한 곳에 약 2초였다(2026-11-18 PROD 기록).
- 계약완료 딜에 심전계 · 산소포화도 · 카트온 수량이 있는 병원은 234곳이다(dev2 사본, 2026-11-13 무렵 데이터). 전부 수집하게 되면 화면을 열 때 계산하는 방식은 수 분이 걸린다.
- 병원별 화면은 바꾸지 않는다. 지금처럼 원본에서 바로 계산한다.

### 5.2 저장

본체 DB에 표 2개를 둔다(Prisma 모델, 일반 마이그 절차). 원본 DB에는 아무것도 추가하지 않는다 — 본체는 원본 DB를 읽기만 한다는 규칙(CLAUDE.md 9)을 그대로 둔다.

| 표 | 한 행 | 값 |
|---|---|---|
| `usage_daily_stats` | 병원 × 날짜 × 판매모델 | 측정 환자 수, 신규 측정 수, 최대 동시측정 수, 계산 시각 |
| `usage_daily_device_stats` | 병원 × 날짜 × 판매모델 × 기기 종류 | 사용 횟수, 최대 동시사용 수, 그날의 계약·공급 수량 (수치 없는 날은 null) |

- 판매모델은 합산 · 일반형 · 사용량비례형 3종을 모두 저장한다.
- 집계 값은 본체 DB의 일일 백업에 포함된다(원본 DB는 백업 방식 미결정 상태).
- 마지막 집계의 시각 · 소요 시간 · 병원 수 · 오류는 설정값 한 행(`usage_stats_last_run`)에 남겨 화면의 '집계 시각'에 쓴다.

### 5.3 갱신

- 본체 앱의 스케줄러가 **1시간마다** 수집 중인 병원을 하나씩 돌며 **최근 91일**(12주 추이에 필요한 범위)을 다시 계산해 덮어쓴다. Agent가 1시간마다 보내므로 그보다 자주 돌 이유가 없다.
- 매번 91일 전체를 다시 계산하는 이유: 늦게 들어오는 데이터(상태 이력 따라잡기, 하루 1회 대조), 딜 수정으로 바뀌는 분모, 산정 기준 변경이 과거 값을 바꾼다. 다시 계산하면 병원별 화면과 항상 같은 값이 된다.
- 91일보다 오래된 행은 그대로 남는다(지우지 않는다).
- 원본 DB에서 사라진 병원(개발 환경으로 PROD 데이터를 동기화한 직후 등)의 행은 갱신 때 지운다.
- 계산은 지금의 `buildUsage`를 쓴다. 한 병원을 한 번 읽어 판매모델 3종을 함께 내도록 고친다(지금은 판매모델마다 다시 읽는다).
- **규모가 커졌을 때**: 한 바퀴가 10분을 넘기기 시작하면 '최근 7일은 매시간, 91일 전체는 하루 1회'로 나눈다. 처음부터 나누지 않는다.
- 주기는 다른 스케줄러처럼 설정값(`usage_stats_interval`, 기본 `1h`, `off` 가능)으로 둔다. 수동 실행은 `scripts/usage-stats-rebuild.mts`.

### 5.4 모듈 경계

- 집계 스케줄러는 `lib/usage/stats-scheduler.ts`에 두고 `instrumentation.ts`가 기동한다. 메인 → `lib/usage` import가 1건 생기므로 승인이 필요하다(D8).
- 화면 · API는 `app/usage/*`, `app/api/usage/overview` — 사용량 모듈 안이다.
- 수신부(`usage-ingest/`)는 건드리지 않는다. 수신부 배포 · 재시작 없음.

## 6. 구현 순서 (승인 후)

1. `buildUsage`를 한 번 읽어 판매모델 3종을 내도록 정리 — 기존 검사(`scripts/usage-metrics-test.mts`)로 결과가 그대로인지 확인
2. 표 2개 마이그 + 집계 저장 함수 + 수동 실행 스크립트 — 집계 값과 병원별 화면 계산을 대조하는 검사 추가
3. 기간 평균 · 판정 순수 함수(`lib/usage/overview.ts`) + 검사
4. API `GET /api/usage/overview?device=&model=` + 화면 + '산정기준' 팝업 절
5. 스케줄러 등록
6. dev2 빌드 후 실제 화면 확인 — dev2 원본 DB에는 수집 데이터가 없으므로 PROD 집계 표본을 넣어 확인

PROD 반영 때는 표 2개 생성(DDL)과 첫 집계 실행이 들어간다.

## 7. 이번 범위가 아닌 것

- 서비스 전체 추이 그래프 — 수집 병원이 늘어나는 동안에는 구성이 바뀌어 추이로 읽기 어렵다
- 측정 환자 수 기준 순위, 측정 환자 / 도입 기기 탭 분리(2026-11-19 보류)
- 가동률 급감 알림(Slack), 판정 기준값을 바꾸는 설정 화면
- 지역 · 담당자 · 병상 규모별 묶음, 병동별 구분
- 엑셀 내보내기

## 8. 확인하지 못한 것

- (2026-11-21 PROD 반영 뒤 첫 결과 — 심전계·합산: 동수원 60%(이전 55%, +5.0%p → 증가), 화순성심 27%(이전 28%, −1.4%p → 유지), 전체 31%)
- **판정 기준(±5%p · 유효일 14일)을 실데이터에 적용해 본 결과가 없다.** 설계 중 PROD 조회가 권한 차단에 걸려 두 병원의 90일 값을 뽑지 못했다. 구현 3단계에서 PROD 값으로 확인하고 기준을 다시 제안한다.
- **계산 소요 시간은 어제 기록(약 2초/병원)뿐이다.** 판매모델 3종을 한 번에 낼 때의 시간, 7일 범위만 계산할 때의 시간은 재지 않았다. → 구현 후 측정: §9.3 (PROD에서는 아직 재지 않음)
- **234곳은 dev2 사본 기준**이다. PROD 현재 값과 며칠 차이가 있을 수 있다.

## 9. 구현 노트 (2026-11-19, dev2·dev)

사용자 지시("일단 dev2와 dev에 구현해줘. 보고 이야기하자")로 §2의 제안값 그대로 구현했다. 결정 항목은 화면을 본 뒤 확정한다.

### 9.1 만든 것

### 9.2 설계에서 구체화된 것

- **최근 30일의 유효 일수는 최대 29일**이다. 병원별 화면의 '최근 30일'이 오늘을 포함한 30일이고 평균에서 오늘을 빼기 때문이다(같은 값이 되게 하려고 그대로 따랐다). 이전 30일은 30일.
- **표의 가동률 칸은 `평균 최대 동시 / 현재 수량 (비율)`** 이고 평균 최대 동시는 소수 한 자리로 적는다. 정수로 반올림하면 `12 / 20 (58%)`처럼 앞뒤가 안 맞아 보인다.
- **변화도 소수 한 자리**(`−3.9%p`). 정수로 적으면 −4.6이 `−5%p`로 보이는데 판정은 '유지'라 어긋난다.
- **12주 추이 선의 세로 범위는 병원마다 따로** 잡는다(최소 10%p 폭). 수준은 숫자로, 선은 오르내림만 본다.
- **수신 지연 병원의 유효 범위**: 마지막 수신일은 하루가 다 들어오지 않았으므로 그 전날까지만 쓴다.
- **전체 가동률의 분모**는 병원별 유효한 날의 평균 수량의 합이다(화면에 적는 `45 / 170대`의 170은 현재 수량의 합). 기간 중 수량이 바뀐 병원이 있으면 둘이 조금 다를 수 있다.
- **스케줄러 첫 실행은 앱 기동 1분 뒤**, 그다음부터 주기마다.
- **기기 상태 이력 조회문을 고쳤다**(`lib/usage/metrics.ts`). DEV 서버에서 화순성심 91일 계산이 조회 시간 상한(20초)에 걸렸다 — `raw_device_status JOIN m`이 통계에 따라 서버 번호만으로 병합 조인을 골라 2억 7천만 행을 비교했다(25초). 측정 코드 목록으로 먼저 좁히도록 바꿔 0.6초, 결과는 기존과 같다(두 병원 해시 대조). 병원별 화면의 주간 통계도 같은 조회를 쓰므로 함께 빨라졌다.
- **dev2 원본 DB에 DEV 서버의 원본 데이터를 복사**해 넣었다(토큰 표 제외). dev2 원본 DB가 비어 있어 화면을 볼 수 없었기 때문이다.
