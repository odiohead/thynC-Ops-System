# 채널톡 AS접수 자동 등록 (channeltalk-as-intake) — 설계안

> **상태: 완료 (2026-09-07 — dev2 E2E 검증·PROD 배포)** (당일 작성 → 시트 실측 v2 → D1·D4·D5 확정 v3 → 사용자 승인 즉시 구현)
>
> 채널톡 경유 AS 접수가 기록되는 구글 스프레드시트('thynC VOC 현황' > 'A/S' 탭 — **채널톡 전용 중계 파일**)를 **1분 주기 폴링**해서 운영관리시스템 AS업무(`/as-receipts`)에 자동 등록하고, 시스템에서 종결되면 시트 완료여부(X열)에 역기입한다. 접수 이후의 모든 처리는 시스템에서 수행(시트에 사람 개입 없음).

---

## 1. 배경·목표

- 고객 AS 문의는 채널톡(ALF Customer 태스크)으로 인입되며, **채널톡 → 구글 스프레드시트 기록은 이미 구현되어 있음**. 채널톡 태스크는 커스텀 HTTP API 호출 미지원("추후 지원 예정") → 시트가 구조화 데이터 접점.
- 사용자 확정: **1분 폴링** 방식 (AS는 사람이 수거·수리하는 업무라 1분 지연이면 실용상 실시간. 웹훅/푸시 불채택).
- 등록 결과(AS코드/실패 사유)를 시트에 되써서 시트에서도 처리 현황 확인 가능하게 한다.

## 3. 전체 흐름

```
[채널톡] ALF 태스크 → 'A/S' 탭 행 추가 (기구현·무변경 — 시트는 채널톡 전용 중계 파일)
────────────────────────────────────────────
[운영관리시스템 — 본 설계 범위, 폴링 틱마다 2가지 수행]
  ① 접수 인입 (시트 → 시스템)
     AA열 공란 & 행번호 > 컷오버 행 읽기
     → 파싱(마이그 파서 재사용): 병원 매칭·시리얼·I열 증상 분배
     → 성공: AS접수 생성 (기존 경로 — 티켓·AS표시·알림·SLA 자동)
     → AA~AD 되쓰기 / 실패: 사유 기입 → 사람 보정 → 재시도
  ② 완료 역기입 (시스템 → 시트)
     AA='등록완료' & X열 미종결 행의 AS코드(AB열)로 접수 조회
     → 시스템에서 종결(완료/취소)이면 X열에 '완료'/'취소' 기입
────────────────────────────────────────────
  이후 처리(수거·발송·교체·완료)는 전부 시스템 /as-receipts에서 수행
```

## 4. 폴링 모듈

- `lib/channeltalk-as-sync.ts` — 동기화 본체. **파싱·매칭 로직은 `scripts/migrate-thync-as-history.mts`의 검증된 코드를 lib로 승격 재사용** (병원 별칭 매처 — NFC 정규화·법인명 폴백 / F열 개행 시리얼 파서 / I열 `SERIAL / 병동 / 증상` 분배)
- `lib/channeltalk-as-scheduler.ts` — `mail-scheduler` 패턴 + **재진입 가드**(이전 틱 미완료 시 스킵)
- `instrumentation.ts` 부트스트랩 등록 (기존 3종 옆)
- 구글 인증: `lib/googleDrive.ts` 서비스 계정 재사용 (spreadsheets 스코프 기보유). **시트에 서비스 계정 편집자 공유 필요** — 조회는 이미 가능 확인(2026-09-07), 되쓰기용 편집 권한 확인 필요
- AppSetting: `channeltalk_as_interval`(`off`/`1m`/`5m`/`10m`, 기본 `off`) · `channeltalk_as_sheet_id` · `channeltalk_as_cutover_row`(컷오버 행번호). 설정 UI는 v1 범위 외(직접 기입)

## 5. 매핑·검증 규칙

1. **병원**: 별칭 매처 유일 매칭만 자동 확정. 0건·복수 후보는 `실패` + 후보명 기재
2. **시리얼**: F열 개행 파싱·정규화(`normalizeSerial`)·중복 제거. G/H 수량과 개수 불일치 시 **경고**(등록은 진행, AC열 기재). 원장 미등록 시리얼은 기존 등록 경로와 동일하게 경고 후 허용
3. **증상**: I열을 시리얼별로 분배(마이그 파서), 매칭 안 되는 잔여 텍스트는 헤더 `note`
4. **자동 등록 조건**: 병원 유일 매칭 AND 유효 시리얼 ≥ 1
5. 날짜: KST 문자열 그대로 파싱(뒤 공백 trim), toISOString 금지(오프바이원 교훈)

## 6. AS접수 생성 — 기존 경로 재사용

- **선행 리팩터링**: POST `/api/as-receipts`의 트랜잭션 로직(발번 P2002 재시도·라인 매칭·AS 표시·티켓 생성)을 `lib/asReceiptService.ts` `createAsReceipt(input, actor)`로 추출 — 화면 등록과 폴링이 같은 함수 사용 (동작 무변경, 회귀 검증 필수)
- 티켓·알림·SLA 기존 파이프라인 그대로: `createTicketForAsReceipt`(CTI = `ticket_domain_cti_rules`) + `notifyTicketCreated` + `syncTicketClocksSafe` (CLAUDE.md 티켓 규칙 1·5 준수)
- `note` 선두 출처 태그: `[채널톡시트 r{행번호}] 고객정보…` — 상세 화면 출처 식별 + **DB측 중복 2차 가드 키**(되쓰기 실패 후 재틱 시 note 태그로 기존재 검사 → 되쓰기만 재수행)
- `preReplace` = P열 `선교체`

## 7. 컷오버·초기 캐치업 (마이그와의 경계)

- AS이력 마이그가 ~9/2 접수분까지 DB 반영 완료(dev2·PROD 3,236+α). 시트는 그 뒤로도 매일 증가 → **컷오버 행번호를 정하고 그 이후 행만 폴링 대상**으로 한다
- 가동 시작 시 1회 캐치업: 컷오버~현재 행(현시점 9/3~9/7 약 40건)을 같은 파이프라인으로 소급 등록하되, **기존 DB 접수와 접수일+병원+시리얼 집합 대조로 중복 검사** 후 진행 (PROD의 실사용 테스트 건 AS-202609-0004 등 충돌 확인)
- 컷오버 이전 행은 마이그 스크립트 영역 — 폴링이 절대 건드리지 않음

### 7.1 완료 역기입 (시스템 → 시트)

- 대상: AA열 `등록완료`이고 X열이 아직 `완료`/`취소`가 아닌 행
- 틱마다 AB열 AS코드로 접수 상태 조회 → 종결 버킷(`resolvedAt` 설정)이면 X열 기입: 완료 → `완료`, 취소 → `취소`
- 도메인 라우트에 훅을 심지 않고 **폴링 틱 내 조정(reconciliation)으로만 수행** — 단일 기록자 유지, 상태 변경 경로(화면 PUT·티켓 역동기화·라인 확정 자동완료)를 전부 자연 커버, 실패 시 다음 틱 재시도로 자가 복구
- ~~역기입은 X열(+AD 처리시각 갱신)만 — 처리 열(L~W)은 시스템이 쓰지 않음~~ → **2026-09-09 개정(D6)**: R·W열 발송정보 역기입 추가(§7.2). 그 외 처리 열(L~Q, S~U)은 여전히 시스템이 쓰지 않음

### 7.2 발송정보 역기입 (시스템 → 시트, 2026-09-09 — 출하정보 안내메시지 발송용)

- 배경: CS가 시트 기준으로 출하정보 안내메시지를 발송하므로 R(수리품 택배발송)·W(발송기기)가 시스템 처리 후에도 채워져야 함 — 설계 §2.1의 "Q~W 미사용" 판단 오류를 정정
- 대상: AA열 `등록완료` 행 전부(X 종결 여부 무관). AB열 AS코드로 접수 조회 → 발송된 라인(`shippedAt` 있고 결과가 수리반환·교체)이 1건 이상이면
  - **W 발송기기** = 출고 시리얼 목록(수리반환 → 원 시리얼, 교체 → 교체기 시리얼) — 라인 id 순, **개행 구분**
  - **R 수리품 택배발송** = 라인 송장 목록(중복 제거, 라인 순) — **개행 구분**
  - **V 발송, 교체일자** = 라인 발송일(`shippedAt`, YYYY-MM-DD) 목록(중복 제거, 라인 순) — **개행 구분** (같은 날 일괄 발송이면 1줄)
- 시점: **완료 시가 아니라 발송정보 입력(라인 처리) 시점부터** 반영. 부분 발송 시 매 틱 조정으로 누적 갱신
- 시트 값과 다를 때만 씀(무의미 쓰기 방지 — 틱당 변경 없으면 0건). 기입 시 AD 처리시각 갱신. X열 완료 역기입(§7.1)과 독립
- 검증(dev2 사본 시트 E2E, 2026-09-09): 2라인 접수 → 1차 라인1 발송(R=송장1, W=시리얼1, X=미완료) → 변경 없는 틱 shipBack 0 → 2차 라인2 발송(R=송장1\n송장2, W=시리얼1\n시리얼2, X=완료) 전부 통과. V열 추가분도 동일 E2E(9/8·9/9 2회 발송 → V=2026-09-08\n2026-09-09) 통과

### 7.3 수거 송장 역기입 (시스템 → 시트, 2026-09-10)

- 배경: 고장품 택배수거 송장을 상세 화면(진행 기록)에서 입력·저장하고, 시트 L열(수거 송장)에도 반영 요청
- 대상: AA열 `등록완료` 행 전부. AB열 AS코드로 접수 `pickupTrackingNo` 조회 → 값이 있고 시트 L열과 다를 때만 L 기입 + AD 처리시각 갱신. DB 값이 비면 시트를 지우지 않음(단방향 채움). 결과 카운터 `pickupBack`
- 검증(dev2 사본 시트 E2E, 2026-09-10): 틱 1회 L 기입 → 변경 없는 틱 pickupBack 0 통과

## 9. 결정 사항

### 확정 (2026-09-07 사용자 확인)

- **D1 — 등록자 계정**: 시스템 계정 **"채널톡 접수봇" 신설 확정**. 로그인 불가 처리·역할 USER(VIEWER 등록 차단 회피)·소속 SEERS — 세부는 P0에서 생성 시 확정
- ~~D2 — 시리얼 필수화~~ → 해소: 최근 200행 시리얼 100% 기입
- **D3 — 초기 상태**: '접수' 고정 (출처는 note 태그로 구분)
- **D5 — 행 작성 주체**: **채널톡 태스크가 신규 행을 자동 추가함 (확정)**. 접수담당자(K)·수거일(M)·발송지(T) 등은 이후 CS 담당자가 보강 → 폴링은 행 추가 직후를 잡되, 접수 필수 필드(A·B·F)가 갖춰진 행만 처리하고 미비 행은 다음 틱 재확인(§5)
- **되쓰기 권한**: 서비스 계정 편집 권한 보유 확인 (사용자)

- **D4 — 동기화 범위 (확정, 2026-09-07)**: **접수만 시트→시스템, 완료는 시스템→시트 역기입.**
  - 시트의 역할은 **채널톡 전용 중계 파일**로 한정 — 채널톡 태스크가 커스텀 API를 미지원해서 못 없애는 것뿐. **향후 사람이 시트에서 처리 작업을 하지 않는다** (처리 열 L~W 기입 중단 — 운영 공지는 사용자 몫)
  - 접수 이후의 모든 처리(수거·발송·교체·완료)는 시스템 `/as-receipts`에서 수행 (기능 기구현)
  - 다만 시트를 열람은 하므로, **시스템에서 접수가 종결되면 X열 완료여부에 되써준다**: 완료 → `완료`, 취소 → `취소` (§7.1)
- **D6 — 발송정보 역기입 (확정, 2026-09-09)**: CS 출하정보 안내메시지 발송이 시트 R(수리품 택배발송)·W(발송기기)에 의존함이 확인되어 **발송정보 입력 시점부터 R·W 역기입** 추가(개행 구분, §7.2). 같은 날 사용자 요청으로 **V(발송·교체일자)도 동일 방식 추가**. D4의 "L~W 미기입" 범위에서 R·V·W를 제외
