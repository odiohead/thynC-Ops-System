## 1. 배경·목표

운영관리시스템 1.0은 **운영 실무(task) 데이터**(답사·설치·유지보수·자재·티켓)를 축적해 왔다.
이번 개발은 새 업무 모듈이 아니라, **영업(Sales/CRM) 정보 축**을 시스템에 추가하는 것이다.

- **중심은 병원(hospitals)**: 병원 상세(기본정보·대웅담당자·thynC현황)를 영업 관점으로 고도화
- **핵심은 데이터 모델** — 어떤 정보를 어떤 구조로 담느냐. UI는 각 Phase에서 화면을 보며 확정 (본 문서의 UI 기술은 최소화)
- **활용**: 축적 후 영업 대시보드·추이 분석·목표 달성도 등으로 확장
- **진행 방식**: 한 번에 전 컬럼을 넣지 않고 **Phase 세분화** — 단계별로 다듬으며 진행

### v2 보완 관점 (사용자 피드백 반영)

1. **매출은 차수(1차·2차·N차) 단위** — 한 병원에 도입이 여러 번 발생. 차수별 가격 + 병원 전체 매출(합계) 둘 다 필요
2. **웨어러블 디바이스 종별 수량** — 어떤 디바이스가 몇 개씩 들어갔는지 차수별·병원별로 파악
3. **대웅 관리체계(사업소·담당자)는 필수 아님** — 병원 마스터의 **하위 테이블**로 분리 (hospitals 본체·프로필에 FK를 심지 않음)
4. **영업일지** — 별도 구조화 테이블 vs 기존 병원노트(위키) 중 결정 필요 (§5.5에 비교·추천)

## 3. 설계 원칙

1. **운영 축과 분리, 연결로 통합** — 영업 데이터는 별도 테이블군(`sales_*`, `hospital_*`)에 두고 hospitals/projects에 FK로 연결. 기존 테이블 컬럼 추가 없음 (hospitals 오염 방지)
2. **병원 = 마스터, 영업 정보 = 하위 테이블** — 프로필(1:1)·키맨(1:N)·대웅 채널(1:N)·딜(1:N)·영업일지(1:N) 전부 hospitals 하위로 매달림. 필수 입력 없음 — 아는 만큼만 쌓는다
3. **일정·상태의 단일 소스는 운영 축** — 공사·답사 일정, 설치 진행 상태를 영업 테이블에 중복 저장하지 않는다
4. **금액·계약 정보의 단일 소스는 영업 축(딜)** — 병원 총매출·디바이스 총수량 등은 전부 **딜 합산 파생값** (별도 저장 금지 — 정합성 깨짐 방지)
5. **마스터 코드화** — 판매가유형·정산상태·매출인식 등 반복 값은 StatusCode 신규 카테고리 (기존 설정 페이지 패턴 재사용)
6. **티켓 미편입** — 영업 정보는 task가 아니므로 티켓 파이프라인·Slack 알림·SLA 대상이 아니다
7. **민감정보 권한 게이트** — 매출 금액은 열람 권한을 좁게 시작 (§6)
8. **비소급·안전 마이그레이션** — 순수 추가 DDL만. 기존 화면 동작 무변경. CLAUDE.md 수동 마이그레이션 패턴 준수

## 4. 데이터 모델 (핵심)

### 4.0 전체 구조

```
hospitals (기존 마스터) ─┬─ 1:1  hospital_sales_profiles   영업 프로필 (전체 병상수·등급·메모)
                         ├─ 1:N  hospital_contacts          병원 측 키맨
                         ├─ 1:N  hospital_daewoong_channels 대웅 관리체계 (사업부·사무소·담당자) ── N:1 sales_offices/sales_reps (마스터)
                         ├─ 1:N  sales_deals                도입 차수(딜) 원장 ★  ── 0..1 projects (운영 연결)
                         │        └─ 1:N  sales_deal_devices  차수별 디바이스 종별 수량 ── N:1 device_infos (기존 마스터 재사용)
                         └─ 1:N  sales_activities           영업일지 (오픈 이슈 ⑧ — 채택 시)

sales_targets (연도별 목표 — 병원 비종속)
```

**파생값(저장하지 않음, 집계로 계산)**
- 병원 총매출 = Σ `sales_deals.amount_actual` (해당 병원)
- 병원 디바이스 종별 총수량 = Σ `sales_deal_devices.quantity` (디바이스별)
- 침투율 = `hospitals.intro_beds` / `hospital_sales_profiles.total_beds`

### 4.1 hospital_sales_profiles — 병원 영업 프로필 (1:1) — P1

| 컬럼 | 타입 | 설명 |
|---|---|---|
| hospital_code | FK hospitals UNIQUE | |
| total_beds | Int? | **병원 전체(허가) 병상수** — 수기. 침투율 분모 |
| total_wards | Int? | 전체 병동수 (선택) |
| grade | String? | 영업 등급/중요도 (A/B/C — 마스터화는 추후) |
| sales_memo | Text? | 영업 메모 |

> v2 변경: 사무소/담당자 FK를 프로필에서 **제거** — 대웅 관리체계는 §4.3 하위 테이블로 분리 (필수 아님·이력 관리 가능).

### 4.2 hospital_contacts — 병원 측 주요 담당자(키맨) (1:N) — P1

| 컬럼 | 타입 | 설명 |
|---|---|---|
| hospital_code | FK hospitals | |
| name / title / department | String | 이름·직책·부서 |
| phone / email | String? | 연락처 |
| role_note | String? | 역할 메모 (구매결정권자, 실무 창구 등) |
| is_primary | Bool | 대표 키맨 |
| is_active / sort_order | | 퇴사·이동 시 비활성 (이력 보존, 삭제 대신) |

### 4.3 대웅 관리체계 — 병원 하위 테이블 + 조직 마스터 — P1

**hospital_daewoong_channels (병원 1:N)** — "이 병원은 어느 사업부/사무소/담당자 라인인가"

| 컬럼 | 타입 | 설명 |
|---|---|---|
| hospital_code | FK hospitals | |
| office_id | FK sales_offices? | 사무소 (선택) |
| rep_id | FK sales_reps? | 담당자 (선택) |
| is_current | Bool | 현재 라인 여부 — 담당 변경 시 이전 행 false 처리 (이력 보존) |
| note | String? | |

- **전 컬럼 선택 입력** — 대웅 정보가 없는 병원도 문제 없음 (UI·DB 모두 병원 본체와 분리)
- 마스터를 두는 이유: 사무소·담당자별 **집계 축**(대시보드 "사무소별 실적")이 필요하고, 자유 텍스트면 표기 흔들림("병원광주2" vs "광주2")으로 집계가 깨짐

**sales_offices (마스터)**: division(사업부: 서울1/서울2/지방1/지방2/지방3) · name(사무소: 병원강원·병원광주2 …) · sort_order · is_active
**sales_reps (마스터)**: office_id FK · name · phone · is_active — **시스템 User 아님** (대웅 영업사원 전원 계정화 불가 전제)
- 기존 `DaewoongHospitalAssignment`(시스템 계정 기반, 운영용)는 그대로 유지 — 역할이 다름

### 4.4 sales_deals — 도입 차수(딜) 원장 (병원 1:N) — P2 ★핵심

엑셀 '도입 현황' 1행 = 1딜. **한 병원의 N번째 도입 = N차 딜.**

| 그룹 | 컬럼 | 설명 |
|---|---|---|
| 식별 | deal_code (`DEAL-YYYYMM-NNNN` 자동 발번), hospital_code FK, **round_no Int** | **round_no = 병원 내 차수(1,2,…N)**. UNIQUE(hospital_code, round_no). 등록 시 다음 차수 자동 제안(수정 가능). 확장 여부는 round_no ≥ 2로 파생 — 별도 플래그 불필요 |
| 운영 연결 | project_code FK? UNIQUE | 선택 (계약 전 딜 존재 가능). 1프로젝트 = 최대 1딜. 일정·공사 정보는 이 연결로 조인 |
| 분류 | hospital_sale_model_id (StatusCode `SALES_MODEL_HOSPITAL`: 구축형/구독형/분납형/사용량), seers_sale_model_id (StatusCode `SALES_MODEL_SEERS`) | 엑셀의 2축 그대로 |
| 규모(스냅샷) | ward_count, bed_count, wards_text(도입병동 "IM, ICU"), depts_text(도입진료과) | 계약 시점 값. 운영 실측은 연결 Project 참조 |
| 금액 | amount_product(제품/구성품), amount_construction(공사비), amount_total(판매 합계), amount_service(용역매출), **amount_actual(실판매액)**, vat_excluded_amount? | BigInt(원). **실판매액이 매출 집계 기준.** 병원 총매출 = Σ 차수별 실판매액 |
| 가격 | price_type_id (StatusCode `SALES_PRICE_TYPE`: 기존/권장/최소/사용량비례/미정) | |
| 일정(영업 소유분만) | first_contact_date(최초 인입일), contract_date(계약일), delivery_date(납품일), warranty_months | 답사·공사일은 저장 안 함 (운영 축 조인) |
| 정산 | settlement_status_id (`SALES_SETTLEMENT`), tax_invoice_status_id (`SALES_TAX_INVOICE`), revenue_recognition_id (`SALES_REVENUE_RECOG`: 수금시작/입금완료/수금완료…) | StatusCode 3종 |
| 기타 | remark Text?, created/updated | |

### 4.5 sales_deal_devices — 차수별 디바이스 종별 수량 (딜 1:N) — P2

"이 차수에 어떤 웨어러블 디바이스/장비가 몇 개 들어갔나"

| 컬럼 | 타입 | 설명 |
|---|---|---|
| deal_id | FK sales_deals (Cascade) | |
| device_info_id | FK device_infos | **기존 장비 마스터 재사용** (심전계 MC200M·산소포화도 MP100W·게이트웨이 MGW1000 등 — 부족한 모델은 마스터에 추가) |
| quantity | Int | 수량 |
| unit_price | BigInt? | 단가 (선택 — 엑셀 실매출정리 시트에 있음) |

- UNIQUE(deal_id, device_info_id)
- 병원별·종별 누적 수량 = 딜 조인 합산 (파생). 전사 종별 누적도 동일
- **ProjectDevice와의 경계**: ProjectDevice = 운영(설치 실측 구성), deal_devices = **계약/판매 시점 수량**. 의도적으로 분리 — 판매 수량과 설치 실측이 다를 수 있음 (오픈 이슈 ⑦에서 단일화 여부 결정)

### 4.6 sales_activities — 영업일지 (병원 1:N) — 오픈 이슈 ⑧ 채택 시

기존 `MaintenanceLog` 패턴 (작성자·시각 자동 + Tiptap 리치 텍스트) 그대로.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| hospital_code | FK hospitals | |
| activity_date | Date | 활동일 (작성일과 별도 — 소급 기록 허용) |
| activity_type_id | FK StatusCode `SALES_ACTIVITY_TYPE`? | 방문/전화/메일/데모 등 (선택) |
| content | Text (Tiptap HTML, sanitize) | 내용 |
| author_id | FK users (SetNull) | 작성자 자동 기록 |
| deal_id | FK sales_deals? | 특정 차수 관련 활동이면 연결 (선택) |

→ 병원노트(위키)와의 비교·추천은 **§5.5** 참조.

### 4.7 sales_targets — 연도별 목표 — P4

- year UNIQUE, target_beds(예: 50,000), target_hospitals?, memo → 달성도 = 누계 실적 / 목표

### 4.8 (P5 후보 — 범위 밖, 필요 시 그 시점 재설계)

- `sales_usage_weekly`: 병원별 주간 사용량 (소스·연동 방식 결정 필요)
- 파이프라인(계약 전 리드/영업기회 단계 관리), 주간 진행보고

## 5. UI 방향 (최소 기술 — 각 Phase에서 화면 보며 확정)

> v2: UI 상세 설계는 의도적으로 뺐다. 아래는 동선 골격만.

- **5.1 병원 상세** — 기존 카드 유지 + '영업 정보' 섹션(권한자만): 프로필·키맨·대웅 채널·**차수별 딜 리스트(1차/2차/N차 + 합계 행)**·디바이스 누적 수량
- **5.2 딜 등록·수정** — 병원 상세에서 진입(차수 자동 제안). 전사 딜 목록(`/sales/deals`)은 P2 후반 화면 보고 결정
- **5.3 설정** — `/settings/sales-offices`(사업부·사무소·담당자), StatusCode 신규 카테고리 관리(기존 StatusCodeManager 재사용), nav 등록 + 시드 SQL(idempotent)
- **5.4 대시보드(P4)** — 엑셀 '요약' 재현: KPI·종별/판매모델/사무소별 분포·월별 추이·목표 달성도·디바이스 종별 누적
- **5.5 영업일지 방식 비교 (오픈 이슈 ⑧)**

| | A. 병원노트(위키) 활용 | B. 구조화 테이블 (sales_activities) ★추천 |
|---|---|---|
| 구현 비용 | 0 (이미 있음) | 소 (MaintenanceLog 패턴 복제) |
| 형식 | 자유 서식 (BlockNote·협업편집) | 엔트리 단위 (날짜·유형·작성자 자동) |
| 시간순 이력·필터 | 불가 (한 문서에 덧붙임) | 가능 (타임라인·기간·유형·작성자) |
| 추이·대시보드 활용 | 불가 | 가능 ("이번 달 영업활동 N건" 등) |
| 권한 분리 | 어려움 (위키 열람 체계 따름) | 영업 권한 게이트 그대로 적용 |
| 딜(차수) 연결 | 불가 | 가능 (deal_id 선택 연결) |

**추천: B** — "쌓아서 추이로 활용"이라는 이번 개발 목표에 부합. 병원노트는 지금처럼 자유 메모/협업 문서로 공존 (역할 분리: 노트 = 서술형 문서, 영업일지 = 활동 이력). 별도 페이지는 만들지 않고 **병원 상세 영업 섹션 내 타임라인**으로 시작, 전사 통합 뷰는 나중에 필요해지면 추가.
