## 0. 결론 요약

**기능 세트와 아키텍처는 상용 대비 충분하다. 새 기능이나 아키텍처 개선은 권하지 않는다.** 노션·컨플루언스·Outline·Docmost가 기본기로 삼는 것 중 이 조직 규모(68명·137페이지·주간 열람자 18~27명)에서 빠진 것은 없고, 메인 업무 시스템 임베드·AI 절 단위 검색처럼 상용에 없는 강점이 있다. 온라인에서 "실패한 사내위키"로 묘사되는 조건(수천 페이지·검색 불능·낡은 문서·1년 뒤 사용자 10%)과 정반대로, 매주 전체 인원의 27~40%가 읽고 14명이 쓰며 가장 많이 읽히는 것이 매주 갱신되는 업무보고다. 여론이 꼽는 실패 원인 1위(낡은 문서)에 해당하는 듯 보였던 구 위키 트리(`Old_thynC…`)도 들여다보니 9월에도 수정되고 대체 페이지가 없는 **현행 인프라 핸드북**이었다 — 오해를 부르는 것은 문서가 아니라 'Old_'라는 이름뿐이다.

**그러나 "지금 그대로 좋다"고는 말할 수 없다.** 2026-06-30 실시간 협업(Yjs) 전환 때 본문 저장 주체가 REST에서 협업 서버로 옮겨졌는데, 그때 같이 옮겨졌어야 할 배선이 끊긴 채 남아 있다. 사용자가 신고하지 않은 이유는 화면(편집기)이 항상 최신 Y.Doc을 보여 주기 때문이고, 그 뒤편의 검색·AI·이력·수정자 표시는 조용히 낡거나 멈춰 있다. 전부 소규모 수정이다.

### 2.2 여론 기준으로 본 판정

온라인에서 반복되는 사내위키 실패 원인은 ① 낡은 문서가 새 문서와 같은 얼굴로 존재해 신뢰가 무너짐 ② 주인 없음 ③ 검색 품질(대부분 수천 페이지 맥락) ④ 도구가 아니라 문화 문제다. 이 위키는 넷 중 어디에도 해당하지 않는다. ①로 의심됐던 `Old_thynC` 트리는 검증 결과 낡은 문서가 아니라 유일한 현행 인프라 핸드북이었다 — 새 트리에 대체 페이지 0, 스위치 설정(09-03)·MySQL설정(09-09)·파트별 역할(09-09) 등이 9월에도 실제 수정, 90일 28명 817회 열람, AI 어시스턴트가 9회 인용. 180일 이상 미수정 페이지는 위키 전체에 0건이다. 검색·구조·에디터 아키텍처를 갈아엎을 근거는 여론 어디에서도 나오지 않는다. "Notion의 USP는 단순함이었는데 기능 비대화로 잃었다"는 반응이 다수라는 점은 이 조직의 "신규 화면은 단순하게" 원칙을 그대로 뒷받침한다.

### 2.3 상용 대비 이미 동급인 영역 (강점 주장 35건 재검증: 유지 27 · 과장 7 · 오류 1)

- **실시간 협업의 편집 계층**: CRDT(Yjs) 동시편집, 커서·이름 표시, 쿠키 JWT를 WS 업그레이드에서 검증, VIEWER 읽기전용을 **서버가 강제**(Hocuspocus가 readOnly 연결의 update를 적용하지 않음을 소스로 확인), 삭제 페이지 연결 거부, 종료 시 flush, 협업 불가 시 읽기전용 폴백이라 split-brain 없음. PROD 협업 서버는 6/30 이후 무재시작.
- **붙여넣기 품질(노션 수준, 실측)**: 마크다운 표 → 표 블록(헤더 행 인식), 워드형 HTML 표 → 굵게 보존, 엑셀 `<th>`·colspan 보존, VS Code 코드 언어 보존, 파일 붙여넣기 업로드.
- **트리·구조**: 순환 참조 BFS 차단(이동 API), 시스템 카테고리(이슈노트·병원 노트) 보호, 하위 동반 휴지통·복원(부모 삭제 시 루트 승격), DB 실측 순환 0·고아 0, id 기반 URL(컨플루언스 Cloud와 동급), 템플릿·휴지통·AI 제외 페이지가 트리·검색·홈에서 일관 제외.
- **첨부**: 영구 URL(`/api/wiki/files/{id}` → 인증 후 presigned redirect)이라 presigned 만료로 이미지가 깨지는 흔한 사고 없음. 본문 파일 URL 중 첨부 테이블에 없는 id 0건.
- **이슈노트 임베드 구조(상용에 없음)**: 프로젝트 상세에서 위키 페이지를 **같은 Y.Doc 세션**으로 협업 편집(34건, 본문 있음 31). 병원/프로젝트 @멘션·명시 참조·역참조 카드는 **보유하나 미사용**(인라인 멘션 0, 일반 참조 0, 병원 노트 6건 중 본문 있음 2).
- **AI 지식 백본(상용 유료 기능의 상위 형태)**: 헤딩 경로 단위 청크 인덱스(경로 훅이 아닌 상태 비교 방식), 헤딩×3·제목×2 가중 랭킹, 절 읽기 + 이웃 절, 카테고리 경로·수정일 동봉, AI 제외 플래그의 계층 cascade. Notion AI(Business, 인당 월 $20)·Rovo(크레딧) 없이 API 종량제. 단 입력이 스냅샷이라 A-1 수정 전에는 표 페이지의 최신 본문을 못 본다.
- **HTML 산출물 파이프라인**: sanitize + `sandbox`(allow-scripts 없음) 이중 방어(실질은 sandbox가 강방어), git 원본 + 멱등 재게시 스크립트, 90일 353회 실사용.
- **마감**: 디자인 토큰(라이트)·Pretendard·토스트/모달/스켈레톤 공통 UI, 모바일 드로어, HTML 페이지 409 충돌 감지, RBAC 가산 규칙을 UI·API 7지점에 일관 적용.

**동급이라 말하면 안 되는 것(검증에서 걷어낸 강점 주장)**: ① 표 — 1차 감사는 "헤더 행/열·셀 병합·셀 색 있어 노션 이상"이라 했으나 BlockNote 0.51.4의 `tables` 옵션(headers·splitCells·cellBackgroundColor·cellTextColor)은 기본 false이고 WikiEditor가 옵션을 넘기지 않아 **에디터 UI에 없다**(DB의 헤더 행 8건은 6월 이관본 산물). 현 상태는 노션 simple table 이하이며, 옵션 한 줄로 켤 수 있다(B-1). ② "검색·AI 청크가 본문과 어긋나지 않는다" — A-1 수정 전에는 거짓. ③ 버전·감사 — A-2·A-3에서 다룬 대로 현재 작동하지 않음(감사 리소스도 `wiki_page` 하나뿐). ④ 백업·운영 — "있다"는 수준(동일 호스트 7일, 오프사이트·모니터링 없음, 29MB 에러 로그 미발견). ⑤ 순환 차단은 이동 API에만 있고 일반 PUT의 `parentId` 경로는 미검사(UI는 안 쓰므로 실사고 없음, A-8에서 함께).

## 4. A. 고쳐야 할 것 — 결함·회귀 (전부 소규모)

A-1~A-5는 모두 협업 서버 한 파일(`collab-server/index.mts`)과 그 주변에 있으므로 **한 번의 협업 서버 배포**(`npm run build:collab` → `pm2 restart thync-collab-prod`)로 묶는다. 이 배포는 6/30 이후 첫 협업 서버 재배포이므로 §6 C-1(배포 절차 문서화)을 반드시 동반한다.

### A-1. 표가 있는 페이지의 스냅샷 동기화가 항상 실패한다 — PROD 확인
- **증상**: 협업 서버 `store()`가 Y.Doc→블록 변환 결과를 JSON 직렬화 없이 Prisma에 넘기는데, BlockNote 0.51.4는 표의 `columnWidths`에 `undefined`를 넣고 Prisma는 배열 안의 `undefined`를 거부한다. PROD 에러 로그에 `스냅샷 동기화 실패` 527회(29MB, 페이지 13개), 검증에서 Prisma 오류 재현. REST 시절에는 클라이언트 `JSON.stringify`가 `null`로 바꿔 통과했으므로 협업 전환 후에만 생긴 결함이다.
- **영향**: Y.Doc은 저장되므로 편집 유실은 없다. 그러나 표가 하나라도 있는 페이지는 이후 모든 편집에서 `content_json`·`plain_text`·백링크가 갱신되지 않고, 청크 스케줄러도 재색인하지 않는다. 현재 표 포함 Y.Doc 11페이지 전부가 대상이고 그중 5페이지가 실제로 갈라져 있다 — 주간 업무보고 07.07·07.27·08.10·08.31(90일 열람 각 87~112회)과 '시스템 아키텍쳐'. 예: '2026.07.27'은 스냅샷 129자 vs 실제 2,926자. **사람 검색·AI 검색(`search_wiki`)·읽기전용 폴백·복제가 낡은 본문을 본다.** 사용자는 "검색이 원래 별로"로 받아들일 뿐 고장으로 인지하지 못한다.
- **해법(소)**: `store()`에 `JSON.parse(JSON.stringify(blocks))` 1줄(같은 문제의 선례가 `scripts/import-notion.mts:143`에 이미 있음) + 1회 재동기화 + 실패 로그를 페이지 id·메시지 1줄로 축약. 재동기화는 tsx 직접 실행이 스키마 로드 실패로 불가하므로 esbuild 번들 엔트리로 만들거나 협업 서버의 `openDirectConnection` 무변경 트랜잭션으로 `store()`를 재실행한다(PROD DB 쓰기이므로 규칙 5에 따라 별도 허락).
- **하지 말 것**: 이 건에 store() 재설계·실패 카운터 대시보드를 붙이지 않는다.

### A-2. 버전 히스토리가 협업 전환 이후 멈춰 있다
- **증상**: `wiki_versions` 57건이 전부 2026-06(마지막 6/30 05:43). 버전 생성은 REST PUT 경로에만 있고 클라이언트는 협업 모드에서 본문을 PUT하지 않는다. 7월 이후 협업 저장이 발생한 페이지 82개(편집 상한 — 서식만 건드리거나 표를 연 저장도 포함)에 버전 0건. 모달 안내문 "본문이 수정될 때마다 직전 상태가 자동 저장됩니다"와 README는 현재 거짓이다.
- **영향**: Y.Doc은 GC 기본값이라 삭제된 문단은 Y.Doc에도 남지 않는다. 일일 덤프(24시간 단위, 7일 보존)가 유일한 백스톱이라 "오전에 쓰고 오후에 지운" 회의 내용은 어떤 백업에도 없다. 복원 실행은 전 기간 0건이므로 피해는 아직 없고, 성격은 보험이다.
- **해법(소)**: `store()`에 REST와 같은 규칙을 이식한다 — 마지막 버전과 N분(기존 2분 또는 Docmost·Outline식 5분) 이상 차이 && 내용 상이 시 `wikiVersion.create`, 저장자는 Hocuspocus가 `store()`에 넘겨주는 `context.user`(디바운스 특성상 "마지막 입력자"). 버전 생성은 별도 try로 비치명 처리. 같은 계열 오픈소스(Outline·Docmost) 모두 협업 persist 훅에서 지연 스냅샷을 만든다. `gc=false` + Y.snapshot 방식은 운영자 후회 사례가 많아 채택하지 않는다.
- **조건**: A-4와 반드시 같은 배포. diff·미리보기는 이번 범위에서 제외.

### A-3. '최근 수정자'가 본문 편집을 반영하지 못한다
- **증상**: `store()`는 `contentJson`·`plainText`만 갱신하고 `lastEditorId`·감사로그를 남기지 않는다. 살아있는 Y.Doc 페이지 81건 중 66건은 마지막 본문 편집자가 어디에도 기록돼 있지 않다. 홈 '최근 수정 by'·페이지 헤더·검색 목록·댓글 알림 수신자(작성자+최근수정자) 10곳이 이 값을 쓴다. 7월 이후 감사 UPDATE 17건은 전부 제목·메타 변경이다.
- **해법(소)**: A-2와 같은 함수에서 `lastEditorId: context.user.userId` 1필드 추가. **단 "내용 상이" 가드 필수** — 검증에서 텍스트 변화 없는 store(서식만 건드리거나 표를 연 경우)가 실재함이 확인됐으므로(표 페이지 11개 중 6개), 무조건 갱신하면 최근 수정자가 열람자로 바뀐다. **감사로그는 `store()`마다 남기면 안 된다**(한 페이지에서 store 318회 실측 — 공용 audit_logs가 위키 소음으로 찬다) — A-2의 버전 스냅샷이 실제 생성될 때 1건만 남기거나 생략한다. 과거 이력은 소급 복구할 수 없다.

### A-4. 버전 '복원'이 협업 페이지에서 겉으로만 성공한다
- **증상**: 복원 라우트는 `content_json`만 되돌리고 진실의 원천 `wiki_page_ydoc`을 건드리지 않는다. 편집기는 그대로 Y.Doc을 보여 주고 다음 `store()`가 스냅샷을 원복한다. 사용자에게는 200 OK·모달 닫힘·감사로그 "(버전 복원)"·새 스냅샷까지 성공으로 보인다. 버전 보유 15페이지 중 11페이지가 해당하며, A-2 이후 새로 쌓이는 버전은 100% 해당한다.
- **해법**: ① 즉시(소, A-2와 동반 필수): Y.Doc 보유 페이지는 복원 버튼 비활성 + 안내, 모달 거짓 문구 수정. ② 실제 복원(소): 검증에서 서버 인프라 없이 되는 경로가 확인됐다 — 페이지를 보고 있는 사용자의 **라이브 협업 세션 안에서 `editor.replaceBlocks`로 복원본을 적용**하면 일반 편집과 같은 경로로 Yjs에 전파되고 Undo도 된다(POST로 현재본 스냅샷 → replaceBlocks 순서). 협업 서버 경유 fragment 교체(중)는 필요 없다. 이 팀은 같은 결함 클래스(REST가 content_json을 직접 써서 Y.Doc과 경합)를 07-26 병원노트 append에서 REST 경로 폐지로 해결한 선례가 있다. **같은 클래스의 잔존 경로 2개도 함께 닫는다**: 제목 변경 시 타 페이지 링크 라벨을 content_json에서 고치는 코드(Y.Doc 미반영·다음 store에서 원복, 링크 6건이라 관찰 수준)와 일반 PUT의 `contentJson` 수용(현 클라이언트는 안 보내지만 스크립트·구 클라이언트가 보내면 분기) — 후자는 Y.Doc 보유 페이지에서 거부.

### A-5. 세션 중 협업이 끊기면 8초 뒤 입력을 조용히 버린다
- **증상**: `WikiEditor`의 8초 타이머는 "한 번도 연결되지 못하면"이라는 주석 의도와 달리 세션 중 끊김에도 발동해 협업 에디터를 최초 로드 스냅샷의 읽기전용으로 교체하고 `provider.destroy()`로 로컬 Y.Doc을 파기한다. HocuspocusProvider 기본값은 무한 재접속이고 Yjs는 끊긴 동안의 편집을 재접속 시 병합하는 것이 존재 이유인데 그걸 스스로 무력화한 셈이다. 협업 서버가 6/30 이후 재시작 0회라 지금까지 발생 증거는 없지만 **A-1~A-4 배포가 첫 트리거**가 된다.
- **해법(소, `WikiEditor.tsx` 1파일)**: 최초 연결 성공 후엔 폴백 생략(provider 유지, 기존 "재연결 시도 중" 표시 유지) + `hasUnsyncedChanges` 기반 `beforeunload` 경고. **예외 필수**: 토큰 만료 등 서버가 4401/4403으로 닫으면 provider가 재시도하지 않으므로 이 경우는 지금처럼 폴백한다. y-indexeddb 같은 로컬 영속화는 추가하지 않는다.

### A-6. 위키에 소속(org) 서버 게이트가 없다
- **증상**: nav 메뉴만 `allowed_org_codes={SEERS}`(2026-08-09 사용자가 메뉴 관리에서 변경)이고 미들웨어·레이아웃·`/api/wiki/*` 42개 핸들러·협업 `onConnect` 어디에도 소속 검사가 없다. AI·영업·상담·주간업무 모듈은 "nav 게이트는 UI일 뿐 API를 막지 못한다"는 주석과 함께 DB 실시간 소속 게이트를 구현했는데 위키만 빠졌다. 비-SEERS 활성 계정은 대웅 VIEWER 1(로그인 이력 없음)·소속없음 2뿐이고 실현 사례 0건이다.
- **왜 그래도 고치나**: 노출 대상 콘텐츠가 가볍지 않다 — 인프라 핸드북 트리에 서버·스위치·게이트웨이 계정/비밀번호, MySQL root 비밀번호, LTE 라우터·사내 Wi-Fi 비밀번호가 **평문**으로 있는 페이지가 여럿이다(§6 메모 참조 — 게이트는 외부 1명을 막을 뿐 내부 65명에게는 여전히 보인다).
- **해법(소)**: `lib/weeklyAccess.ts`식 "SEERS OR `wiki.access`" 가산 게이트를 레이아웃·API 공용 가드·협업 `onConnect` 3지점에 적용(Next 미들웨어는 edge라 Prisma 불가). 병원·프로젝트 상세의 노트 임베드는 403 시 패널 숨김. 무소속 내부 계정 2개(부트스트랩 관리자 포함)는 소속 부여 또는 `wiki.access`로 처리 — **사용자 결정 필요**. 병행: 휴면 외부 계정 비활성화.

### A-7. 영구삭제·첨부삭제가 USER 전원에게 열려 있다
- **증상**: 같은 DELETE 핸들러에서 이슈노트·병원노트는 휴지통 이동조차 ADMIN/`wiki.admin`으로 막아 두고, 그 아래 `?permanent=1` 분기는 USER 누구나 하위 전부 hard delete + S3 첨부 즉시 삭제를 허용한다. 휴지통 여부도 검사하지 않아 API로는 살아있는 카테고리 루트에도 통한다. 첨부 삭제 API는 클라이언트 호출처가 0건인 죽은 엔드포인트다. 버전 복원도 USER 전원 가능(현재본을 스냅샷으로 보존하므로 위험은 낮음). 실사용 0건.
- **해법(소)**: `permanent`일 때 `isAdminOrAbove OR (isUserOrAbove AND wiki.admin)` + `deletedAt` 필수, 휴지통 버튼 숨김, 첨부 DELETE 핸들러 삭제, `wiki.admin` 카탈로그 설명에 복원·영구삭제 범위 갱신. **주의**: RBAC Lite "가산 전용" 원칙상 USER의 기존 접근을 빼는 정책 변경이므로 사용자 명시 승인 필요. 협업 `onConnect`의 `isActive` 미검사는 로그인 API가 비활성 계정을 거부해 실효가 없으므로 제외.

### A-8. 신규 페이지가 정렬값 0으로 들어가 형제 순서가 뒤섞인다
- **증상**: 페이지 생성 API가 `sortOrder`를 지정하지 않아 0으로 삽입되고(137페이지 중 59가 0, 동률 그룹 8개), ↑↓ 이동은 값 교환 방식이라 0↔0이면 무반응, 형제 조회가 휴지통 페이지를 거르지 않으며 클라(제목)·서버(생성일) 동률 규칙이 다르다. 최다 열람 '주간업무'에서 매주 새 페이지를 만드는 5명이 돌아가며 **↓를 7번 눌러 맨 아래로 내리는 흔적**이 감사로그·updated_at에 남아 있고, 07.27이 07.20 앞에 있는 역순이 7주째 그대로다.
- **해법(소)**: 생성 시 `max+1`(복제 라우트에 이미 있는 규칙), ↑↓ 시 살아있는 형제만 화면과 같은 규칙으로 0..n 재부여 후 교환. **범위 가드**: 이슈노트·병원노트 생성 경로는 손대지 않는다(현재 가나다순 유지). 자동정렬 플래그 옵션은 추가하지 않는다. A-11②와 같은 파일이므로 함께. 같은 김에 일반 PUT의 `parentId` 경로에도 이동 API와 같은 순환 검사를 건다(현재 자기 자신만 검사, UI 미사용 경로).

### A-9. 슬래시 메뉴의 커스텀 항목이 기본 동작을 덮어써 생긴 결함 2건
- **증상**: ① 커스텀 콜아웃·구분선 항목이 `insertBlocks(after)`만 호출해 "/" 입력으로 남은 빈 단락 아래에 블록을 넣고 커서를 옮기지 않는다 — `/콜아웃` 선택 후 타이핑이 위 빈 줄에 들어가 고장처럼 느껴진다(콜아웃 사용 0건의 유력 원인 중 하나, 인용 48건·배경색 42건이 대체 사용 중). ② 기본 스펙과 같은 키 `divider`를 커스텀 스펙으로 덮어써 슬래시 메뉴에 "Divider"와 "구분선"이 둘 다 뜨고, 기본 스펙의 `---` 입력규칙·`<hr>` 붙여넣기 파싱을 잃었다.
- **해법(소)**: ① `@blocknote/core`의 `insertOrUpdateBlockForSlashMenu`로 교체 ② 커스텀 divider 스펙·항목 삭제(저장 형식 동일, 마이그레이션 불필요). 고쳐도 콜아웃 사용량이 늘 것이라 기대하지 말 것.
- **분리**: 에디터 UI 한글 사전(ko) 적용은 결함이 아니라 언어 변경이고, 0.51.4 ko 사전에는 `/table`·`/heading`·`/bullet` 영문 별칭이 없어 6월부터 영문 슬래시에 익숙해진 편집자 습관을 깨므로 §5 B-4 선택 항목으로 뺀다. 콜아웃 색은 파란색 고정(변경 UI 없음)이라 주의·경고 용도로는 못 쓴다 — 고치더라도 색 팝오버까지는 이번 범위 밖.

### A-10. 우측 고정 목차가 노트북 해상도에서 본문 위에 겹친다
